Kaneo：自带 24 工具 MCP 的开源项目管理神器，把 Jira/Linear 装回自己机房

发表于 2026-08-11 分类于 开源项目 ， 效率工具
Kaneo 是一款 MIT 协议、自带 24 工具 MCP Server 的极简项目管理工具，单日 491 star 上 GitHub Trending，让 AI Agent 也能直接读写你的看板。

你的团队有没有过这种时刻：项目经理在 Linear 上排好 Sprint，开发在 GitHub 上提 Issue，结果两边数据对不上，状态总要人工同步？或者公司出于合规要求不让把任务数据放到 SaaS，但你又不想回到 Jira 的” 配置地狱”？今天 trending 上的 usekaneo/kaneo 正好戳中这两个痛点 —— 一款 MIT 协议、自带 24 工具 MCP Server 的开源项目管理工具，单日 491 star、累计 5,943 star，已经稳坐 GitHub Trending 今日第二。

项目背景：为什么是” 现在”

过去一年，”AI Agent 操作业务系统” 从一个 PPT 上的口号变成真实需求。Linear 在 2025 年初率先推出官方 MCP Server，Jira 通过 Marketplace 插件跟进，Plane 在 2026 年 3 月补上了原生 MCP。但凡用过的人都会发现一个共同问题：MCP 只是 SaaS 厂商给的” 附加功能”，你的项目数据仍然躺在别人机房里。

Kaneo 走了一条相反的路：先把项目管理系统本身做轻做透，再把 MCP 作为” 一等公民” 内置到产品里。它的自我定位很直白 ——“All you need. Nothing you don’t.” 核心原则有四条：

  1. Self-hosted first：项目数据、权限、审计全部在你自己的服务器上
  2. Minimal by default：默认界面只暴露看板、任务、优先级这些” 每天 80% 时间会用到的” 功能
  3. Fast on small hardware：在 2 核 4GB 的小 VPS 上依然顺滑
  4. Open source (MIT)：可以随便改、随便集成、随便商用

仓库地址：https://github.com/usekaneo/kaneo，官方文档站：https://kaneo.app。

核心功能亮点

1. 看板 + 列表 + 甘特图，一种工作流三种视图

Kaneo 的对象模型非常克制，只有 Workspace → Project → Task 三层。Task 支持状态、优先级、负责人、标签、子任务、附件、评论等核心字段，没有 Jira 那种自定义字段、自定义工作流引擎。但通过” 项目模板”+” 自定义状态” 组合，依然能覆盖 Scrum、看板、简单甘特排期三种主流场景。

甘特图是 v2 之后补上的关键能力：每个 Task 都可以设置起止日期，跨任务的依赖关系通过” 阻塞 / 被阻塞” 关系推导，自动在时间线上画出连线。比起 MS Project 这种庞然大物，Kaneo 的甘特图胜在” 够用就好”。

2. 24 工具 MCP Server：让 AI Agent 直接动手

这是 Kaneo 在 2026 年最被讨论的差异化能力。每个 Kaneo 实例自带一个 HTTP MCP 端点 /api/mcp，同时官方也发布 npx -y @kaneo/mcp 给 stdio 客户端用。24 个原生工具覆盖：

  • 任务维度：create_task、update_task、assign_task、move_task（改状态）、comment_on_task
  • 项目维度：create_project、list_projects、archive_project
  • 看板维度：list_boards、create_column
  • 标签 / 成员 / 优先级等元数据管理

实际场景里，这意味着你可以在 Claude Desktop、Cursor、Continue 甚至自家 Agent 里直接说：

“把 #backend 项目里所有 P0 的 bug 列出来，按负责人分组，assignee 是我的标红”

Claude 会在你授权下调用 list_tasks 拿到数据，再调用 update_task 把优先级调整到 P0。整个过程不需要 RPA 抓页面、不需要写 Selenium 脚本，结构化 API 一次到位。

3. Self-host 一条命令，资源占用友好

Kaneo 在 v2.6.0 之后推出了单体镜像 ghcr.io/usekaneo/kaneo:latest，把原本的 web/api 合并成一个进程（仍是 TypeScript + Hono 后端 + React 前端，分层清晰但部署只有一个容器）。配套 PostgreSQL，标准 docker compose up -d 就能起来。

对只想跑着试试的开发者，官方还提供 drim CLI 工具，本地一条命令 drim up 就能在 http://localhost:5173 看到完整功能。2 核 4GB 的小 VPS 推荐配置 10GB 硬盘空间就够。

4. 团队协作：邀请、权限、公开只读链接

Kaneo 的协作模型非常” 工程师友好”：

  • 认证方式：本地邮箱密码、GitHub OAuth、Google OAuth、Discord OAuth 都内置了
  • 角色：Owner / Admin / Member / Viewer 四级
  • 公开只读链接：把项目以”roadmap” 的形式分享给外部 stakeholder，不会泄露工作区其他内容
  • GitHub 集成：双向同步 Issue 和 Task—— 关闭 GitHub Issue 时对应 Task 自动完成

第四步：体验 rlm 风格的工作流

“用 kaneo MCP 拉出 #backend 项目过去 24 小时的 completed 任务、本周 in_progress 任务、所有被阻塞的任务，按 markdown 表格输出，每行附 task 链接。”

Cursor 会自动调用 list_tasks（带 status、updated_after 过滤），整理成可贴到群里的格式。对个人开发者来说，1 个 MCP 工具能抵一个实习生。

适用场景和限制

适合谁

  • 小到中型研发团队（3–30 人）想要一个轻量、能自托管的看板工具
  • 对数据合规有要求的公司 —— 金融、医疗、政企的内部项目管理
  • 重度使用 AI 编码助手的团队，希望 Agent 能直接读写任务系统
  • 不想被 SaaS 涨价绑架的独立开发者 / 工作室

不太适合谁

  • 需要复杂工作流引擎（多级审批、SLA、自定义字段类型）——Jira 仍然更专业
  • 需要时间追踪 + 工资单 + 发票 —— 这不是 Kaneo 的定位
  • 需要大规模跨地域协作（1000+ 人、几十个项目并行）—— 需要企业级 RBAC、审计日志，Kaneo 还在路上
  • 完全不愿意自己运维 ——Plane Cloud / Linear / Jira Cloud 仍是更省事的选择

与同类项目的差异

维度 Kaneo Linear Plane OpenProject
协议 MIT（自托管版 Apache） 闭源 AGPL-3.0 GPL-3.0
自托管 ✅ 一条命令 ❌ ✅ ✅
原生 MCP ✅ 24 工具 ✅ 官方 ✅ 官方 ⚠️ 企业版插件
资源占用 极低（2C4G） - 中（4C8G 起） 中高
学习曲线 极低 极低 低 中等

可以看到，Kaneo 的独特生态位是” 轻量 + 自托管 + 原生 MCP” 三者的交集。如果你正在寻找” 够用就好” 的看板系统、又想把 AI 嵌进日常工作流，它非常值得花一个下午试用。

总结

Kaneo 不是一个会让你 WOW 的产品，它不会重新发明项目管理。它厉害的地方在于把” 开源 + 自托管 + AI 可操作” 这三件事同时做对了：MIT 协议让你不担心被收编，单体镜像让你 5 分钟跑起来，原生 24 工具 MCP Server 让你的 AI Agent 真正动手改任务而不是只读不改。

在 AI Agent 越来越像” 数字员工” 的今天，能被 Agent 安全地读写、结构化地操作，是项目管理工具的下一个分水岭。Kaneo 押对了一半 —— 另一半要看它在多租户、审计、企业级权限上能不能继续跟上。但对个人和小团队来说，现在装一个玩玩完全值得。
