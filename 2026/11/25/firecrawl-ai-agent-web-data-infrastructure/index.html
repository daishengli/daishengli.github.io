firecrawl/firecrawl：20.9 万 star 的 AI Agent 抓取基础设施，AGPL-3.0 开源自托管，一个 Rust 二进制把网页变成 Markdown

发表于 2026-11-25 分类于 开源项目
firecrawl/firecrawl 是 GitHub 上星标最多的 AI Agent 数据基础设施项目之一，累计 208914 个 star、10916 个 fork，AGPL-3.0 协议（SDK 为 MIT），主语言 TypeScript，2024 年 4 月建仓至今高频提交。它是一套把网页变成干净 Markdown 的清洗引擎加统一 API，核心能力包括 scrape 单页抓取、crawl 整站爬取、map 站点 URL 发现、batch scrape 批量抓取、search 搜索、interact 浏览器交互、agent 自主取数，以及 Alexandria 的 550 多个数据源。项目提供三种形态：apps/local 是 Rust 单二进制，不依赖数据库队列容器，可本地跑抓取、把 v2 API 服务在 3002 端口并以 MCP 接入 Claude Code、Cursor、Codex 等；apps/api 是 Docker Compose 编排的完整自托管服务端，含 API、worker、Playwright、Redis、RabbitMQ、NuQ PostgreSQL；Firecrawl Cloud 是官方托管服务，宣称 96% 网页覆盖率与 3.4 秒 P95 延迟。仓库另含 Python、Node.js、Go、Java、Rust、Ruby、.NET、PHP、Elixir 九套 SDK。

firecrawl/firecrawl：20.9 万 star 的 AI Agent 抓取基础设施

一、先说一个我踩过的坑

上个月我给自己的 AI Agent 装了一套「网页阅读」能力。用着挺顺，直到有一天我让它去查一个供应商的 API 定价页，它拿回来的内容是这样的：

整段东西有 60% 是导航菜单和页脚，剩下的才是真正的价格表。然后 Agent 就开始编 —— 它盯着一个价格表格的截图结构，硬生生给我拼出了一个”Enterprise 方案每月 $500” 的价格表。

我一开始以为是模型幻觉，直到我把同一段 HTML 直接喂给它看，问题就清楚了：不是模型笨，是喂给它的东西太脏。一个 800KB 的 HTML 里，真正有信息量的可能只有 3KB，剩下的全是 <nav>、<footer>、cookie 弹窗、广告位和无限滚动加载的骨架屏。

Firecrawl 就是来解决这件事的。一句话概括它的定位：

把任意网页变成一份干净的、可以直接塞进 AI 上下文里的 Markdown。

它现在在 GitHub 上是 208914 个 star、10916 个 fork，AGPL-3.0 协议，主语言 TypeScript，仓库从 2024 年 4 月建到现在还在天天提交，open issues 有 917 个。这是我写博客以来第一次在 star 数上被一个” 抓取工具” 级别的项目震到 —— 说实话，我一开始以为 AI Agent 赛道里刷星最狠的一定是模型或者 IDE。

更有意思的是，它并不是一个云 API 的闭源后端。这个仓库里同时塞着完整的服务端源码、一个 Rust 编写的本地单文件二进制、以及九套 SDK。你可以完全不用它的云服务。

二、它到底想解决什么问题

Firecrawl 官方的自我描述是 “Knowledge infrastructure to make your agents smarter”—— 让 Agent 更聪明的知识基础设施。这句话听起来很虚，但拆开看它其实指一件很具体的事。

2.1 Agent 的上下文不是给定的，是要” 抓” 的

今天绝大多数 AI Agent 的知识来源是训练时烧进去的静态语料。想让它知道今天的新闻、某个库的最新版文档、某家公司的最新定价，就只能上网抓。

但” 上网抓” 这件事有巨大的坑：

坑一：HTML 噪音。 现代网站的 HTML 里，正文内容可能只占 20%。剩下的是导航、侧边栏、弹窗、埋点脚本、SEO 文本、推荐位。直接把 HTML 塞给模型。一是烧 token（一个页面轻易几百 KB），二是干扰模型 —— 它会把导航里的” 登录 / 注册” 当成页面标题。

坑二：JavaScript 渲染。 现代前端站点（尤其是 Next.js/ Nuxt / Svelte 这类 SPA）服务端返回的 HTML 里根本没有正文，内容全靠前端 JS 跑出来。用 curl 抓就是一个空壳。

坑三：格式不统一。 PDF、Word、PPT、Excel 要单独写一套解析逻辑，而且解析出来的还是乱序的。

坑四：站点结构。 你想抓整个文档站 200 页，得自己写递归、限流、断点续传、去重。

Firecrawl 把这四件事全包了。

2.2 一个功能矩阵先看懂

README 里有一张表，我第一次读的时候没太当回事，看完文档才明白这张表才是整个项目的设计核心：

Feature Firecrawl Local Firecrawl Cloud
Scrape Markdown, HTML, raw HTML and links Adds structured JSON, summaries, screenshots and browser actions
Crawl, Map and Batch Scrape ✅ ✅
PDFs and Office documents ✅ ✅, plus Parse for uploaded files
Search Through Firecrawl Cloud, no account needed ✅
Alexandria Through Firecrawl Cloud after login ✅
Interact, Agent and Monitor ✅

看懂这张表，你就能理解 Firecrawl 的整体架构思路了。

它把能力分成了三层：

  1. 纯本地层（scrape /crawl/map /batch scrape / 文档解析）—— 这是最核心的清洗能力，本地二进制用 Rust 实现，不依赖数据库、队列或容器，零配置。
  2. 需要索引的层（search）—— 本地笔记本没有搜索引擎索引，只能走云。
  3. 需要大模型 / 大集群的层（interact /agent/ Alexandria /monitor）—— 需要 LLM 驱动浏览器、需要 550+ 数据源的庞大后端，只能走云。

第 2、3 层是” 合理的云依赖”，第 1 层是” 本地必须能跑”。这个切分做得非常克制，我在后面会展开讲。

2.3 关键数字（全部来自仓库 API / README，非估算）

Stars 208914、Forks 10916、License AGPL-3.0（SDK 和部分 UI 组件为 MIT）、主语言 TypeScript（本地二进制为 Rust）、创建于 2024-04-15、Open issues 917、最新 release v2.11.0（2026-06-19 发布，此前有 v2.10、v2.9.0、v2.8.0、v2.7.0）。

3.3 用法三：在本地跑 Firecrawl API

本地实际提供的路由（来自 apps/local/README.md）：

Route What it does
POST /v2/scrape Scrape one URL
POST /v2/map List a site’s URLs
POST /v2/crawl, GET and DELETE /v2/crawl/{id} Start, check and cancel a crawl
POST /v2/batch/scrape, GET and DELETE /v2/batch/scrape/{id} Start, check and cancel a batch scrape
GET /health Health check

三个必须知道的限制：

  • 其它所有 /v2 路由（比如 /v2/search）会转发到 Firecrawl Cloud，除非设 FIRECRAWL_CLOUD=off。
  • v0 和 v1 路由不提供。
  • crawl 和 batch job 存在内存里，任务开始一小时后过期。

这三个限制说实话，暴露了本地版和完整版的差距 —— 内存态队列意味着进程重启任务就没了，重启后正在跑的爬取任务也会丢。

3.4 用法四：完整自托管服务端（Docker Compose）

apps/api 是完整的 Firecrawl 服务端。它的依赖栈在 SELF_HOST.md 里写得很清楚：

Compose 运行 Firecrawl API 和 worker、Playwright、Redis、RabbitMQ、NuQ PostgreSQL，以及可选队列后端的 FoundationDB 服务。默认只有 API 端口发布到宿主机，端口 3002。

也就是说，自托管要跑起来的组件是：Firecrawl API + Worker、Playwright、Redis、RabbitMQ、NuQ PostgreSQL，以及可选的 FoundationDB。

Docker Compose 的编排文件在仓库根目录的 docker-compose.yaml，Kubernetes 清单在 examples/kubernetes/cluster-install，Helm chart 在 examples/kubernetes/firecrawl-helm。

SELF_HOST.md 里那份「首次运行保持简单」的清单，我觉得是全仓库最有价值的文档之一：

  • Release：锁死一个确切 tag。 主分支和浮动镜像标签会独立变化，先审目标 release 的 Compose 文件。
  • API 认证：USE_DB_AUTHENTICATION=false。 认证要在 provision 好数据库 schema 和应用配置之后再加，光改这一个变量不构成完整的认证部署。
  • 队列：默认用 NuQ PostgreSQL，除非你明确要设 NUQ_BACKEND=fdb 并且准备好运维 FoundationDB。
  • 抓取：用自带的 Playwright，加 basic fetch 兜底。
  • AI 能力：默认没有模型 provider，需要时接 OpenAI、OpenAI 兼容端点或 Ollama。
  • 队列管理 UI：默认关闭，要用就配一个强 BULL_AUTH_KEY 并限制网络访问。

文档最后那句总结特别实在：

自托管给你源码和基础设施的控制权，但安全、可用性、容量、升级、数据留存和合规也都归你。

以及一句我觉得该抄下来的警告：

检入的 Compose 文件是一个与源码对齐的起点，不是生产架构。

六、关键设计取舍

抛开功能，这套设计里有几个决策我觉得非常值得拆开讲。

6.1 取舍一：本地优先，还是云优先？

Firecrawl 的答案是本地优先，云兜底。

它可以完全本地跑的部分：scrape、crawl、map、batch scrape、PDF/Office 解析、还有本地 serve 的 v2 API。

它明确交给云的三件事（apps/local/README.md 给的理由）：

Feature Why it goes to the cloud Account needed
Search There is no search index on your machine No, keyless search is rate limited
Pages that refuse your machine When a site blocks -
Alexandria 数据在云端 Yes

这里有个细节：默认情况下，本地单页抓取如果在你机器上加载不了，会被送去 Firecrawl Cloud 抓，结果里标记 "source": "firecrawl-cloud"。

这个 fallback 策略我一开始觉得有点” 背叛本地优先” 的承诺，但你仔细想就明白了 —— 它解决的正是” 某个站点专门封了你的 IP” 这个最烦人的场景。用户拿到了能用的结果，同时能明确知道这个结果是云端来的。

而且可以完全关掉：FIRECRAWL_CLOUD=off，一切留在本机。

Keyless 模式也值得提：不需要 API key 就能用 MCP、CLI 和 API，每月 1000 个免费 credits，而且无 key 的 Cloud 调用是限速的。

6.2 取舍二：单二进制 vs 完整微服务栈

Firecrawl 同时提供这两种形态，看起来是重复投入，其实是精确切分：

  • 要” 能用” 的 → cargo install firecrawl-local，一条命令，不需要 Docker，不需要理解 Redis/RabbitMQ/NuQ/FoundationDB。
  • 要” 可控 / 可扩展” 的 → Docker Compose / K8s / Helm，自己掌控数据留存、升级节奏、合规。

这是开源基础设施项目成熟的标志。只给完整微服务栈的门槛太高；只给单二进制的可控性不够。

6.3 取舍三：复用你机器上的浏览器，而不是内置

Firecrawl Local 不内置 headless browser，而是用你机器上已有的 Chrome/Chromium 渲染需要 JS 的页面。

好处：省几百 MB 依赖、避开 Chromium 版本跟协议不兼容的问题、顺便还帮你做了页面缓存。

代价：首次渲染速度取决于你机器的浏览器启动速度，而且遇到反爬严格到识别浏览器的站点，共享的浏览器 profile 反而更容易被标记成” 自动化流量”。

6.4 取舍四：默认遵守 robots.txt

README 结尾有一句：

最终用户有责任在抓取时尊重各网站的政策。 用户被建议遵守适用的隐私政策和使用条款。默认情况下，Firecrawl 尊重 robots.txt 指令。

这个默认值选得很对。对比一下很多爬虫框架默认无视 robots.txt，Firecrawl 在合规上更保守 —— 虽然这意味着你抓某些站点会拿到 403。

七、和同类项目比一比

这个赛道其实挺拥挤的，我把主要的几个放一起对比。

7.1 对比 Crawlee（Apify 生态）

Crawlee 是 Node.js 生态最成熟的爬虫框架，核心强项是爬虫编排：请求队列、重试、并发控制、请求指纹、防重、Session 池、代理轮换、数据集存储（Dataset / RequestQueue）。

维度 Firecrawl Crawlee
核心定位 网页 → 干净 Markdown 请求编排 / 爬虫运行时
编程模型 配置 + 调用 API 写 JS/TS 代码
输出 Markdown / JSON / 截图 原始结构化数据
队列 / 重试 / 代理 Cloud 版托管，自托管版有 一等公民，非常成熟
AI Agent 接入 原生 MCP + CLI init 需要自己包一层
语言 9 种 SDK + Rust 本地二进制 主要是 JS/TS，也有 Python 版
协议 AGPL-3.0 + MIT Apache-2.0

结论：Crawlee 是” 给工程师的爬虫框架”，Firecrawl 是” 给 Agent 的数据层”。你要是想自己写一套复杂的抓取逻辑（登录、翻页、表单交互、状态机），Crawlee 更合适；你要是想让 Agent 直接拿到能读的网页，Crawlee 帮不上太多忙 —— 它不产出 Markdown。

7.2 对比 Scrapy

老牌 Python 爬虫框架，架构成熟、有 Middleware 机制、生态庞大。差异：Scrapy 输出的是 Item（你定义结构），你得自己写清洗逻辑把它变成 Markdown；Firecrawl 直接给你能塞进上下文的成品。Scrapy 免费（BSD 协议），Firecrawl 核心是 AGPL。

如果你要抓的站点结构稳定、量大、要长期维护，Scrapy + 自己的清洗 pipeline 是更经济的选择。Firecrawl 的价值在”Agent 临时要读一个网页”。

7.3 对比 Browserbase / Browserless / Stagehand

这是浏览器基础设施赛道，做的是” 托管一个真浏览器给你用”。区别在于粒度：Browserbase 给你浏览器，Stagehand 给你 AI 驱动的浏览器操作抽象，Firecrawl 给你已经洗好的内容。

有意思的是 Firecrawl 现在也在往这个方向走 ——interact 和 agent 就是 AI 驱动的浏览器操作。所以 Firecrawl 实际上是从” 内容抽取” 往上打到了” 浏览器操作”。

7.4 对比 Jina Reader / Apify / Tavily

Jina Reader（r.jina.ai）思路跟 Firecrawl 很像：给个 URL，还你干净的 Markdown。优势是零部署。但 Firecrawl 有几个能力是它没有的：站点级 crawl、map、结构化 JSON、schema 化 agent 取数、交互、以及完整的自托管。

Apify 是托管的爬虫平台，Actor 生态丰富，商业化很成熟。Firecrawl 更偏” 给 Agent 用的”——MCP 集成、CLI init 自动改 Agent 配置、schema 输出。Apify 更偏” 给运营团队用的”—— 可视化、定时任务、数据集管理、Actor 市场。

Tavily / Exa 是搜索 API 赛道。Tavily 专做搜索，Exa 做向量搜索。Firecrawl 现在也有 search，且搜索结果直接带 markdown 正文 —— 功能上和 Tavily 重叠了。差异点是：Firecrawl 的 search 和 scrape 是同一个抽象下的两种模式，可以无缝组合；而且它有本地模式。

八、真实局限：说点不好听的

我不打算把 Firecrawl 吹成完美的。这篇文章如果只夸不骂，那对读者没价值。

8.1 AGPL-3.0 是一道商业门槛

README 的 License 段落写得很清楚：

本项目主要采用 GNU Affero General Public License v3.0（AGPL-3.0）授权。SDK 和部分 UI 组件采用 MIT 协议。

AGPL 的关键触发点是：如果你通过网络提供服务给用户，并且修改了 Firecrawl，那你也必须开源你的修改。

这意味着：

  • 自托管做企业内部使用：没问题，AGPL 不触发。
  • 自托管做成对外服务：触发。
  • 只在 SDK 层集成而不碰服务端代码：SDK 是 MIT，相对宽松。

AGPL 在企业内部” 自托管不外传” 的场景是安全的 —— 这恰好覆盖了大多数自托管的动机。但一旦你要做产品，这个协议会成为法务会议上的议题。

8.2 自托管的组件栈不轻

回头看那个栈：

六个组件。对” 我只是想抓个网页” 来说太重了。而且 SELF_HOST.md 里已经明说了：

  • 默认没有持久化卷（root Compose 文件没给 NuQ PostgreSQL、Redis、RabbitMQ 定义持久卷）。
  • 默认 API 无认证（USE_DB_AUTHENTICATION=false）。
  • 管理 UI 默认关闭。
  • PostgreSQL 配置和 API 值要保持一致，内置的 pg_cron 配置指向默认 postgres 数据库。
  • 依赖端口默认应保持私有。

这些都是「这不是生产架构」的明确声明。我如果真要上生产，必须自己补：认证、TLS 终止、网络策略、持久化、备份、监控、资源限制、扩缩容触发器、升级和回滚流程。

这就是「自托管给你控制权，但控制权是要用运维人力换的」的真实含义。

8.3 本地版的功能缺口

前面表格里已经列了，本地版没有：structured JSON、summaries、screenshots、browser actions、Interact、Agent、Monitor、Parse（上传文件）。

而且本地版 crawl job 在内存里，一小时后过期，进程重启就没了。

8.4 Cloud 依赖不是完全可选的

即使你用本地二进制，search 还是要走云。Alexandria 更是只在云上，自托管的服务器明确不包含它。

如果你做的是涉敏数据或者内网环境 —— 内网自托管 + FIRECRAWL_CLOUD=off 是唯一真正闭环的方案，此时你得接受上面说的所有功能缺口。

8.5 抓取本身就是有对抗的

Firecrawl 再强也绕不过反爬。README 自己说 Cloud 覆盖 96% 的网页 —— 反过来理解就是有 4% 抓不到。

而且它默认遵守 robots.txt，意味着尊重 robots.txt 的站点你会拿到拒绝。这是合规和覆盖率之间的必然取舍。

8.6 数字都是官方自己说的

“96% 覆盖率”、”P95 3.4 秒”、”550+ 数据源”、”250M+ 人员”—— 这些全部来自 Firecrawl 自己的 README 和他们自己的 benchmark 页面。它们没有第三方独立验证。 我在文章里原样引用，但读者应该清楚这是厂商自述。

8.7 star 数的信号要打折

20.9 万 star 很夸张。但要冷静看：

  • 这个项目 2024 年 4 月成立，两年半做到 20 万 star，在 AI 赛道这个速度不算特别罕见。
  • 它有商业版（Cloud），star 和商业获客是强相关的。
  • AGPL + 商业 SaaS 的组合，意味着 star 数里有一部分来自” 我想用云服务” 而不是” 我想自托管”。

这不代表项目不好，但代表 star 数在这里不能直接当成” 自托管用户数” 来理解。

九、适合谁，不适合谁

9.1 非常适合

① 你在做 AI Agent，需要让 Agent 能读网页。

这是最核心的场景。你不需要理解抓取细节，Agent 直接调用 MCP 工具就能拿到干净内容。firecrawl-local init 一条命令接进 Claude Code / Cursor / Codex，这个体验是目前同类里最顺的。

② 你需要把文档站整体灌进知识库 / RAG。

crawl + limit + --out ./pages，产出的是一堆干净的 markdown 文件，直接进向量库。map 还能先做 URL 发现。这一整条链路省掉了大量胶水代码。

③ 你在处理「格式很脏」的非 HTML 文档。

PDF、Word、PPT、Excel 本地解析，输出统一格式。这在企业内网场景里价值极高 —— 那批没人愿意维护的老系统文档页，全是 Word 导出的。

④ 你要合规、要数据不出境。

自托管 + FIRECRAWL_CLOUD=off，抓取全在你自己的机器上。对于法务明确要求” 数据不能出境” 的场景，这是唯一可行路径。

⑤ 你在做网页数据的 CI/CD 监控。

crawl 返回 job ID，可以挂到定时任务里，对比历史快照。配合 map 做站点结构变更检测。

9.2 不太适合

① 你的需求是” 长期高频抓同一个大站”。 那用 Crawlee 或 Scrapy 更合适。它们在请求队列、代理轮换、失败重试、断点续传、指纹规避这些” 工业化爬虫” 问题上积累了几十年，Firecrawl 在这些上不是它的战场。

② 你不想引入任何外部依赖。 注意 AGPL 和 Cloud 依赖。真要完全自托管，你要自己养 Redis、RabbitMQ、PostgreSQL、Playwright。

③ 你需要爬高反爬站点。 默认遵守 robots.txt + 共用本机浏览器 profile，碰到 Cloudflare 这类会直接吃瘪。专业反爬对抗需要自己搭指纹和代理池。

④ 你只是要读几个固定页面。 如果你的场景是” 读 5 个已知 URL”，直接 requests + trafilatura 或者更简单的 html2text 就够了，引入 Firecrawl 是杀鸡用牛刀。

⑤ 你需要闭源商业产品。 AGPL 的传染性会直接卡住这条路。除非你只用 MIT 授权的 SDK 层。

9.3 我的实际建议路径

如果你正在考虑集成，我会这么走：

第一步：先用 CLI 试，别一上来就部署。

看输出质量是不是符合预期。清洗质量不行，先别往下走。

第二步：本地二进制试。

验证” 在你的机器上能不能抓到”。

第三步：接进 Agent。

第四步：确认是否真的需要自托管。

如果你的场景是” 团队内部查文档”，很可能不需要 —— 用 Keyless（每月 1000 免费 credits，无需 API key）或者 Cloud 就够了。真要自托管，再去啃 SELF_HOST.md 那套。

十一、结语

Firecrawl 做到 20 万 star，我一开始是不太理解的。写完这篇的过程中我逐渐明白了它做对的几个点：

第一，它把” 脏活” 藏起来了。 Agent 生态真正缺的不是” 又一个 HTTP 客户端”，而是一个” 网页 → 可用上下文” 的可靠转换层。Firecrawl 恰好站在这个位置上，而且用 MCP 把接入成本压到了一条 init 命令。

第二，它没有把” 本地” 和” 云” 做成二选一。 一个 Rust 单二进制 + 一个完整 Docker Compose 栈 + 一个托管云，三种形态共存，各自覆盖不同场景。这种” 全都给你，你自己选” 的做法，在基础设施项目里是很少见的诚意。

第三，它的文档写得比代码还认真。 SELF_HOST.md 里那句「检入的 Compose 文件是一个与源码对齐的起点，不是生产架构」，以及默认关闭认证、默认不开管理 UI、默认无持久化卷这些选择 —— 主动告诉用户” 这里还有坑”，这种诚实在国内的开源项目文档里是稀缺的。

当然，AGPL 是硬门槛，Cloud 的 96% 覆盖率是自说自话，本地版功能缺口明显，自托管的运维成本不低。这些我在第八节都写清楚了。

如果你正在做 Agent，我的建议很直接：先跑 npx -y firecrawl-cli@latest scrape <你常抓的网站>，用三十秒看看输出质量。 如果清洗结果让你惊喜，那就顺着这篇文章往下看；如果还是不满意 —— 那多半是你的场景该用 Crawlee，而不是 Firecrawl。
