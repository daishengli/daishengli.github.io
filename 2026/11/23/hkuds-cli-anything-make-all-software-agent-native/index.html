HKUDS/CLI-Anything：63603 star 的开源项目，把 40 多个专业软件变成 AI Agent 能用的命令行

发表于 2026-11-24 分类于 开源项目
HKUDS/CLI-Anything 是一个由香港大学数据智能实验室出品的开源项目，核心主张只有一句话——让任何有代码库的软件都能被 AI Agent 以命令行方式驱动。它提供一套 Claude Code 插件、SKILL 规范和多平台适配（Claude Code、Cursor、OpenCode、OpenClaw、Codex、Pi、Qodercli 等），把 GUI 软件的后端引擎包装成带 --json 输出、状态化 REPL、undo/redo 和真实渲染验证的 Python Click 命令行工具。项目采用 Apache-2.0 协议，当前 63603 star、5776 fork、291 个开放 issue，主语言 Python，要求 Python 3.10 以上；仓库里已内置 GIMP、Blender、LibreOffice、Inkscape、Audacity、Shotcut、Kdenlive、OBS Studio、Godot、n8n、QGIS、FreeCAD、Joplin、Zotero 等 40 多个软件适配器，累计 2464 个测试全部通过。配套的 cli-anything-hub 包管理器（PyPI 版本 0.4.1）可以一条命令浏览、安装、升级和卸载社区做的 CLI。它的方法论写在一份 HARNESS.md 里，明确要求调用真实软件渲染而不是自己复刻，README 也直说依赖前沿大模型、只对有源码的软件有效、常常需要多轮 refine 才能到生产可用。

一、我被 GIMP 的自动化劝退了整整三年

先说个我自己踩过的坑。

我业余做点视频剪辑，用的 Kdenlive。这东西的界面挺好，剪切、关键帧、轨道，鼠标一拖就完事了。但每次我想批量处理一批素材的时候，就会陷入一种特别难受的处境：

打开 Kdenlive，导入 12 个视频，手动在时间线上摆好轨道，加转场，调音量曲线，导出。做完之后发现文件名错了，改一遍再来。如果这 12 个素材要每周处理一次，那就是每周重复 40 分钟的纯鼠标劳动。

我想过写脚本。但 Kdenlive 的项目文件是 MLT XML，你得先理解它的节点结构、filter、transition 是怎么组织的，才能正确改写它。更麻烦的是，改完 XML 还不算完 —— 有些视觉效果是「渲染的时候」才生效的，你在 XML 里看到的参数和最终画面不是一回事。

于是我写了个半成品脚本，处理了两次之后就放弃了。不是因为 Python 不会写，是因为「用代码可靠地驱动一个专业 GUI 软件」这件事本身，比我想象的要难一个数量级。

这正是 HKUDS/CLI-Anything 想解决的核心问题。它的 README 里有一句话挺直白：

AI agents are great at reasoning but terrible at using real professional software.

翻译一下：AI 推理很强，但用专业软件很废。

现在的方案无非三条路：GUI 自动化（截图、点击、写像素坐标）、用软件官方 API（很多专业软件压根没有 API，或者 API 覆盖了 10% 功能）、或者自己复刻一个简化版（功能缺失一大半）。

CLI-Anything 选了第四条：不碰 GUI，也不复刻功能，而是找到软件真正的后端引擎，直接包装成命令行。

二、它是什么：把 GUI 软件的后端拆出来，套一层命令行

一句话定义：

CLI-Anything 是一个 Agent 原生（agent-native）的软件接口生成方法论 + 工具链：把任意一个有源码的软件，转换成一个 AI Agent 可以可靠驱动的结构化命令行工具。

仓库结构上有意思的一点：它不是「一个生成器脚本」，而是一个单仓库（monorepo）—— 里面既有方法论文档（HARNESS.md），也有 40 多个已经生成好的 agent-harness/ 目录，每个目录都是一个可以直接 pip install -e . 的独立 Python 包。

它想解决什么

README 把目标写成了三句话：

  • Universal Access — 每个软件通过结构化 CLI 瞬间变成 Agent 可控
  • Seamless Integration — Agent 无需 API、无需 GUI、无需重建就能控制任何应用
  • Future-Ready Ecosystem — 一条命令把人类设计的软件变成 Agent 原生工具

而它选 CLI 作为载体，给了六条理由：

特性 说明
结构化、可组合 文本命令天然匹配 LLM 的表达形式，能串成复杂工作流
轻量、通用 几乎零额外依赖，跨系统都能跑
自描述 --help 就是自动生成的文档，Agent 可以自己发现能力
已被验证 Claude Code 每天通过 CLI 跑上千条真实工作流
Agent 优先 结构化 JSON 输出消灭了解析复杂度
确定性 结果一致，Agent 行为可预测

这六条里，最被低估的是第三条：--help 自描述。这意味着一个 Agent 不需要有人手写 API 文档给它，它自己 --help 一遍就知道这个工具能干什么、有哪些参数。这是 MCP 之外另一条「让模型自己摸索」的路子。

三、核心机制：7 阶段流水线

整个项目的灵魂是一份 747 行的文档：cli-anything-plugin/HARNESS.md。它自称是「the single source of truth」，是一套把 GUI 应用变成 Agent 可用 CLI 的标准作业流程（SOP）。

7 个阶段如下：

Phase 1：代码库分析

这一步的目标是找到软件真正的「引擎」，而不是包装它的界面。SOP 给了五条操作：

  1. Identify the backend engine —— 大多数 GUI 应用把表现层和逻辑层分开了，找到核心库 / 框架（比如 Shotcut 的 MLT、GIMP 的 ImageMagick）。
  2. Map GUI actions to API calls —— 把每个按钮点击、拖拽、菜单项，都对应到一个函数调用上，编成目录。
  3. Identify the data model —— 项目状态用什么格式表示？XML、JSON、二进制还是数据库？
  4. Find existing CLI tools —— 很多后端自带 CLI（melt、ffmpeg、convert），这些就是现成的积木。
  5. Catalog the command/undo system —— 如果软件有 undo/redo，那它多半用了 command pattern，这些 command 就是你的 CLI 操作。

第 1 步和第 4 步是这个方法论成立的前提：你不是在给 GUI 写自动化脚本，你是在给软件的后端库写 API。

Phase 2：CLI 架构设计

SOP 建议的交互模型是「两者都要」：

  • Stateful REPL —— 面向交互式 Agent 会话，保持上下文
  • Subcommand CLI —— 面向一次性脚本和流水线
  • Both（推荐） —— 一个 CLI 同时支持两种模式

命令组按软件的逻辑域划分：项目管理（new/open/save/close）、核心操作、导入导出、配置、会话 / 状态管理（undo/redo/history/status）。

状态模型要回答三个问题：命令之间什么必须持久化？状态存哪（REPL 内存 vs CLI 文件）？怎么序列化（JSON session 文件）？

输出格式：人类可读表格 和 机器可读 JSON 都做，用 --json 开关切换。

Phase 3：实现

实现顺序是有讲究的：

  1. 先做数据层 —— 直接操作 XML/JSON 项目文件
  2. 加 probe/info 命令 —— 让 Agent 能先「看」再「改」
  3. 加 mutation 命令 —— 一个逻辑操作一个命令
  4. 加后端集成 —— 一个 utils/<software>_backend.py 模块包装真实软件的 CLI
  5. 加渲染 / 导出 —— 生成合法中间文件，再调真实软件转换
  6. 加会话管理 —— 状态持久化 + undo/redo
  7. 加统一皮肤的 REPL

Phase 6.5：SKILL.md 生成

这是 2026-03-16 加进来的功能，也是让整套东西能被 Agent 自主发现的关键。

每个生成的 CLI 都会附带一个 SKILL.md，遵循 Agent skill 的标准格式：

正文包含安装前置、命令语法、命令组、用法示例，以及给 Agent 的专门指导（JSON 输出、错误处理）。

生成方式是 skill_generator.py，直接从 CLI 的 Click decorators、setup.py 和 README 里抽取元数据，也可以用 Jinja2 模板 templates/SKILL.md.template 定制。

产物位置有点讲究：canonical 版本放在仓库根的 skills/cli-anything-<software>/SKILL.md（这样整个 monorepo 可以直接被 npx skills add HKUDS/CLI-Anything --list 发现），同时在 cli_anything/<software>/skills/SKILL.md 留一份兼容副本，这样 pip install 之后安装好的 harness 也能带上 skill 文件。REPL 启动横幅会优先显示仓库根的 canonical 路径，找不到才回退到包内副本。

Phase 7：PyPI 发布与安装

关键规则是 PEP 420 namespace package：cli_anything/ 目录没有 __init__.py（是命名空间包），每个子包（gimp/、blender/ 等）有 __init__.py。

这样所有 CLI 都能装进同一个 cli_anything 命名空间，互不冲突，同时可以用一条 pip install -e . 装到 PATH 上。

四、五个核心设计原则

README 的「Core Design Principles」写得很清楚，这五条基本决定了整个项目的性格。

1. 真实软件集成

We build structured interfaces TO software, not replacements.

我们构建的是「指向软件的」结构化接口，不是替代品。

SOP 把这条列为 #1 rule，并且措辞强硬：

The real software is a hard dependency. The CLI MUST invoke the actual application for rendering and export — not reimplement the software’s functionality in Python. Do NOT gracefully degrade to a fallback library.

不许用 Pillow 代替 GIMP，不许自己写渲染器代替 Blender。软件没装就报错，并且错误信息里要带安装指引。

为什么这么执着？因为「复刻」出来的实现和原软件的行为差距很大 —— 滤镜参数怎么算、色彩空间怎么处理、编解码器支持哪些，这些细节几十页文档都写不全。而调真实软件，就永远一致。

2. 灵活的交互模型

每个 CLI 同时有两种模式：有状态的 REPL（给交互式 Agent 会话用）+ 子命令接口（给脚本和流水线用）。不带参数运行 → 进 REPL。

3. 一致的用户体验

所有生成的 CLI 共用同一个 repl_skin.py：品牌化横幅、样式化提示符、命令历史、进度条、标准化格式。

这在多工具协同里很重要 ——Agent 在 cli-anything-blender 和 cli-anything-gimp 之间切换时，看到的交互契约是一样的。

4. Agent 原生设计

每条命令都内置 --json，同时保留人类可读的表格。Agent 通过标准的 --help 和 which 命令发现能力。

5. 零妥协依赖

真实软件是硬依赖，没有 fallback，没有优雅降级。SOP 的原话很硬气：

Tests fail (not skip) when backends are missing, ensuring authentic functionality.

后端缺失时测试失败（不是跳过），以确保功能是真的。

这一条和第 1 条有点矛盾 —— 上面表格里确实有 skip 的测试 —— 但整体原则是：能测真的一定测真，实在没法测的（需要付费账号、需要特定 GPU 的）才 skip，并且显式标注。

七、HARNESS.md 里那些「踩过坑才知道」的教训

HARNESS.md 的价值有一大半在「Critical Lessons」这张表上。这些不是从原理推出来的，是被真实 bug 教育出来的。

教训 内容
Use the real software CLI 必须调用真实应用渲染。不许用 Pillow 替代 GIMP，不许自写渲染器替代 Blender。生成合法项目文件 → 调用真实后端。
The Rendering Gap（渲染鸿沟） GUI 应用是在渲染时才应用特效的。如果你只改项目文件却用了个朴素的导出工具，特效会被静默丢弃。解法：原生渲染器 → 滤镜翻译 → 渲染脚本。
Filter Translation（滤镜翻译） 在格式之间映射特效时（MLT → ffmpeg），要注意重复滤镜合并、交错流顺序、参数空间差异，以及根本无法映射的特效。
Timecode Precision（时间码精度） 非整数帧率（29.97fps）会导致累积舍入误差。用 round() 而不是 int()，显示时用整数运算，测试里允许 ±1 帧容差。
Output Verification（输出验证） 永远不要因为退出码是 0 就相信导出成功了。要验证：magic bytes、ZIP/OOXML 结构、像素分析、音频 RMS 电平、时长检查。

「The Rendering Gap」这一条，正好是我开头说的那个 Kdenlive 困境的官方描述。当年我放弃的时候，就是被这个坑住的 —— 以为改完 XML 就完事了，实际上转场和特效一个都没生效，而且没有任何报错。

HARNESS.md 里给的验证方法论具体到了这种程度：

「竖屏视频在横屏帧里约有 40% 黑像素」这种细节，是真的被测试逼出来的。

八、Preview 与 Live Preview：给 Agent 一个「看一眼」的机制

这是 2026 年比较新的一个方向，HARNESS.md 里有一整节规范。

Preview 支持在 harness 层面是可选的，但一旦暴露了有意义的中间视觉 / 检查状态，就必须遵守统一契约，这样人和 Agent 才能在不同软件间用同样的方式推理。

规范里几条要点：

  • 不要从 GUI 窗口截屏做预览 —— 预览产物必须由真实后端产出，或由原生检查 / 导出路径产出
  • Producer 和 Viewer 角色分离 —— harness 通过 cli-anything-<software> preview ... 发布预览状态；cli-hub previews ... 是只读消费者（inspect/html/watch/open），不应该被当成渲染路径
  • 共享预览 bundle 协议 —— 支持预览的 harness 应该产出 preview-bundle/v1 格式的 bundle，bundle 是契约，渲染器仍然是真实软件
  • Live preview 要区分 head 和 history —— session.json 是可变的当前 head，每次捕获产生一个不可变的 bundle 目录，trajectory.json 是只追加的命令到预览历史
  • 别把 _bundle_dir 当永久构建标识 —— 它只是一次快照路径，稳定的 live replay 应该锚定在 session_dir + trajectory.json
  • preview live status --json 要让 Agent 便宜 —— 应该包含紧凑的 trajectory_summary，这样 Agent 不用去读 trajectory.json 就知道最新的命令到 bundle 的映射
  • 必须有 preview recipes /capture/latest，Diff 类工具还要有 preview diff

README 的 Real-World Demos 章节提到，FreeCAD 和 Blender 的 demo 用到了「Preview、Live Preview 和 Trajectory 循环」来产出真实产物 ——CAD 构建、3D 场景、图表、游戏画面、字幕等等。

对 Agent 来说，这个机制的价值在于：它能低成本地看到自己刚才那一系列操作产生了什么，而不是盲写一串命令然后祈祷结果正确。对做长链路生成任务（比如「搭一个 CAD 模型然后渲染出来」）的 Agent 来说，这是闭环里最关键的一环。

九、跟同类项目比一比

CLI-Anything 不是这个赛道上的第一个项目，但它选了一个很特别的位置。

vs MCP（Model Context Protocol）

MCP 是当下最热的 Agent 工具接入协议，生态更大，官方背书，Claude Desktop / Cursor 都原生支持。

对比：

维度 CLI-Anything MCP
接入方式 生成真实命令行 定义工具 schema，走 MCP server
需要对方配合吗 不需要，只要软件有源码 / 后端 CLI 需要服务端实现 MCP 协议
交互模式 REPL + 子命令，有状态 通常是无状态请求 / 响应
生态规模 小（40+ 内置 + 社区） 极大，官方 server 数百个
长任务 天然支持（进程常驻） 需要额外设计

CLI-Anything 的 README 提到过 MCP 桥接 —— 比如 ArcGIS Pro 的 demo 描述是「Live Agent Cartography via the MCP Bridge」，Unreal Editor 的 UEAtelier 也是「MCP self-extension workbench with a Python CLI proxy」。所以它更像是在 MCP 生态的缝隙里补位：MCP 只能覆盖那些愿意做 MCP server 的软件，剩下的靠 CLI 兜底。

而且有个现实优势：CLI 是 UNIX 世界的原生接口。已经有几千个专业软件的 CLI 了，CLI-Anything 不需要说服厂商做任何事 —— 它直接去调。

vs UI 自动化（Playwright、Selenium、Computer Use）

  • Computer Use（让模型看屏幕点鼠标）是最通用的，但它慢、贵、不确定。同一个任务跑两次结果可能不同。
  • Playwright / Selenium 稳定，但只适用于网页，且仍然要处理选择器脆弱问题。

CLI-Anything 的口号是：

No screenshots, no clicking, no RPA fragility. Pure command-line reliability with structured interfaces.

它自己的 README 说 CLI-Anything 可以「flat-out replace GUI-based agent approaches」。

但它比 UI 自动化多一个维度：UI 自动化只能操作 GUI 能暴露的东西，CLI-Anything 操作的是后端引擎的全部能力。一个 GIMP 的 CLI 理论上能做的操作，比它的 GUI 菜单还多（GUI 没暴露的参数，CLI 层可以直接调）。

vs 自己手写 API 封装

很多团队确实会针对自己的业务软件写 API wrapper。区别在于：

  • 手写是 N 个软件 N 遍，CLI-Anything 是一套方法论 N 个软件
  • 手写的质量取决于写的人，CLI-Anything 有 HARNESS.md 这种被 2464 个测试检验过的 SOP

vs Anthropic 的 Claude Computer Use / 各类 GUI Agent

这个更接近。它们的思路是「通用电脑操作」，CLI-Anything 的思路是「把专业软件编译成专用命令」。

我认为区别在于任务类型：通用电脑操作适合「打开浏览器搜个东西」这种一次性、模糊的任务；CLI-Anything 适合「批量转换 200 个文件并且保证每个都正确」这种需要确定性和可验证性的任务。

最后两行我特别想提一下。

硬件控制那一行，SOP 里写了「safety-gated detect, preflight, jog, and framing commands with machine profiles」—— 安全门控的探测、预检、点动、构图命令，加上机器配置档案。激光切割机这种设备，直接让 Agent 点鼠标是很危险的；有明确的安全前置检查流程，是这类工具能不能被 Agent 使用的底线。

Tired of juggling fragmented web service APIs? Feed the docs or SDK manuscripts to /cli-anything and your agents get a powerful, stateful CLI that wraps those individual endpoints into coherent command groups.

把散乱的 API 包装成一个有状态的 CLI。这个思路是把「几十次零散 API 调用」变成「一个工具」，既省 token 又有语义。

十一、真实局限：说几个我不吹的地方

README 自己列了三条 Limitations，我原样翻译，再补几条我的观察。

README 官方承认的三条

1. 需要强模型

CLI-Anything relies on frontier-class models (e.g., Claude Opus 4.6, Claude Sonnet 4.6, GPT-5.4) for reliable harness generation. Weaker or smaller models may produce incomplete or incorrect CLIs that require significant manual correction.

它点名要 Opus 4.6 / Sonnet 4.6 / GPT-5.4 这个级别的模型。弱模型生成的 CLI 可能不完整或不对，需要大量手工修正。

这条很关键 —— 这意味着用便宜的小模型跑一遍是没有意义的。你省下的 API 费用会被后面的人工修正成本吃掉。

2. 依赖源码

The 7-phase pipeline analyzes and generates from source code. When the target software only provides compiled binaries that require decompilation, harness quality and coverage will degrade substantially.

只有二进制、需要反编译的软件，质量会大幅下降。

3. 通常需要多轮 refine

A single /cli-anything run may not fully cover all capabilities. Running /refine one or more times is often needed.

一次生成通常覆盖不全，得反复 refine。

我补充的几条

4. 上游软件的版本漂移

这个 README 没写，但实际用起来会遇到。生成的 CLI 是基于某一版源码的后端行为写的。上游软件一升级，参数名改了、默认行为变了、某个 filter 改名了，你的 CLI 就开始行为不一致。

SOP 里「Filter Translation」和「Timecode Precision」那两条教训，本质上都是因为上游行为比文档更复杂。

5. 上游软件的安装成本经常被低估

CLI-Anything 生成完就完了，但你要用它，得把 GIMP / Blender / LibreOffice / QGIS 都装上，装对版本，装上它们各自的插件和依赖。Kdenlive 还要 FFmpeg，Godot 要 headless 环境。

这跟「一键生成」的宣传给人的心理预期有落差。README 里的警告是必要的，但警告得不够显眼。

6. 291 个开放 Issue

63,603 star 的项目有 291 个开放 issue、5,776 fork、100+ 贡献者。这是一个活跃但也确实嘈杂的社区。Issue 数量本身不说明质量，但说明这个项目还在快速演化，接口可能会变。

7. 星标增速异常

创建于 2026-03-08，到 2026-11-24 大约 8 个半月，63,603 star，日均约 260 star。这个增速在 GitHub 上属于极快的级别（README 里挂了 Trendshift 和 Star History 的徽章）。

我不做阴谋论，但客观说：这个增速明显高于它技术含量所对应的自然曲线。star 数在这里是声望指标，不是质量指标。如果你要评估「这项目能不能用」，该看的是 2464 个测试、HARNESS.md 的详细程度、以及 40 多个 harness 的实际可用性，而不是 6.3 万这个数字。

8. 测试数量 ≠ 测试深度

2464 个测试听起来很唬人，但要拆开看：blender 208 passed (150 unit + 58 e2e)，unit 占大头。unit test 用的是合成数据。真正证明「能用」的 E2E 部分，每个 harness 大概只有几十个。

而且这些测试是它自己的 harness 自己的测试，测的是「这个 harness 符不符合 HARNESS.md 的规格」，不是「这个 harness 能完成真实复杂任务」。README 的 Roadmap 里有一条还没打勾：

  • Benchmark suite for agent task completion rates

也就是说，「Agent 用这个 CLI 完成任务的成功率」这个真正该关心的指标，目前还没有基准测试。

9. 部分 harness 还标着 experimental

比如 NotebookLM CLI 是「experimental」，OpenCode 平台是「Experimental」，Goose 和 Qodercli 标着「Community」。这些说明集成的成熟度参差不齐。

十二、适合谁，不适合谁

适合

  • 做 Agent 产品的团队 —— 你需要一个能把 Agent 接到真实专业软件上的可靠方案，不想自己写集成
  • 有大量重复性图形 / 文档工作的人 —— 批量处理素材、生成报告、画图表，这些一旦能 CLI 化就是数量级的效率提升
  • 内部工具多、没有 API 的组织 —— 老系统、闭源系统、专业桌面软件，只要能找到后端引擎就能包
  • 做 GUI Agent 的研究者 —— 它提供了一条跟 Computer Use 完全不同的技术路线，HARNESS.md 是可以直接拿去当论文素材的方法论
  • 想学「怎么给 LLM 设计工具接口」的人 —— HARNESS.md 的「Output Verification」「Fail loudly and clearly」「Provide introspection」这几条，是通用工具设计原则

不适合

  • 只有闭源二进制、拿不到源码的软件 —— 官方承认质量会大幅下降
  • 用不起前沿模型的团队 —— 小模型生成出来的 CLI 得不偿失
  • 一次性任务 —— 装 GIMP + 让 Agent 迭代三轮的成本，比你手动做一次还高
  • 要求 100% 稳定的生产场景 —— 上游漂移、多轮 refine、Issue 数量都说明它还在快速变化
  • 只是想「试试 AI 能不能用 Blender」 —— 为什么不直接用 Blender 自带的 Python API？

十三、我的判断

说点我自己的看法。

CLI-Anything 最有价值的部分不是那 40 多个 harness，而是 HARNESS.md。

40 个 harness 明天可能就过时了 —— 上游软件一升级就得跟。但「怎么给一个 GUI 软件造 Agent 接口」这件事的方法论，是可以长期复用的：

  1. 找后端引擎，不要包装界面
  2. 先做 probe/info 命令，让 Agent 先看再改
  3. 真实软件是硬依赖，不许降级
  4. 每个命令都要 --json
  5. 输出必须验证，不能信退出码
  6. REPL 是默认模式，因为 Agent 需要跨命令保持上下文

这六条，无论用什么协议（MCP、HTTP、gRPC）、在什么框架上，都是对的。

另外我觉得「SKILL.md 自动生成」这步是这个项目最聪明的地方。它把「工具的说明书」变成了工具构建过程的一部分，而不是事后补的文档。这意味着：

  • 文档不会过期（因为是从 Click decorators 里抽的）
  • Agent 拿到 CLI 的同时就拿到了说明书
  • --help（人类）和 SKILL.md（Agent）两条发现路径共存

63,603 star 里有多少是给这个设计买单的，我不好说。但 100+ 贡献者、40 多个真实可用的 harness、2464 个测试、747 行的方法论文档 —— 这些是真金白银的工程量，不是包装出来的。

它现在最缺的东西，README 的 Roadmap 里写得很清楚：任务完成率基准测试。有了那个，「这个 CLI 到底好不好用」才有客观答案，而不是靠 demo 视频和 star 数。

十四、上手建议：三条路径怎么选

你的情况 建议
只想用现成的 pip install cli-anything-hub → cli-hub search <关键词> → 装一个试试
想让 Agent 自主选工具 装 cli-hub-meta-skill，然后用自然语言下指令
想给自己的软件造 CLI 装插件 → /cli-anything ./your-repo → 反复 /cli-anything:refine
想研究方法论 直接读 HARNESS.md 的「Architecture Patterns & Pitfalls」和「Critical Lessons」两节
想读代码 挑一个 harness 看 cli_anything/<software>/utils/<software>_backend.py，那是最能体现设计意图的文件

我的个人建议是：先用一个你已经熟悉的软件（比如 GIMP 或 LibreOffice），读它的 agent-harness/ 目录，然后再决定要不要用在自己的项目上。看懂一个 harness 的结构，比看 40 个 demo 有用得多。
