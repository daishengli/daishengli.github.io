iamajmeena/neonclipping：2927 star 的本地 AI 剪辑引擎，把 85 分钟直播剪成竖屏短视频只要 97 秒

发表于 2026-11-28 分类于 开源项目
neonclipping 是印度 Jaipur 的导演 Ajay K Meena 用 Python 写的本地短视频剪辑引擎，2026 年 11 月 19 日上线，五天后拿到 2927 个 star 和 194 个 fork，AGPL-3.0 许可证（2026 年 11 月 24 日之前发布的版本仍是 MIT）。它解决的是 OpusClip 这类云端剪辑服务的核心痛点：一条 85 分钟的直播录屏上传上去要等几十分钟还按分钟计费、素材还留在别人服务器上。它最核心的思路是「音频优先」——先只下载 79 MB 音频，用 YouTube 自带的逐词字幕拿到 transcript，靠响度突变、2-4 kHz 人声能量、optical flow 运动量和静音到爆发过渡打分挑出候选片段，再让本地 Ollama 模型读候选段落的文字打分、写标题和 hook，最后只下载被选中那几秒视频片段，用 FFmpeg 烧录字幕输出 1080x1920 竖屏成片。README 实测 RTX 2060 上 85 分钟 YouTube 直播剪 3 条用 97 秒，3 小时 Twitch VOD 用 136 秒。项目还包含 11 种主播画面布局、5 种字幕样式、52 种字幕语言、自动找摄像头框的 YuNet 人脸检测、基于聊天热度突增的直播实时剪辑、手机远程控制、本地 MCP 接口给 Agent 调用，以及直接发布到 YouTube、Instagram、TikTok 的凭证对接。全部跑在本地，服务默认只监听 127.0.0.1。

iamajmeena/neonclipping：2927 star 的本地 AI 剪辑引擎，把 85 分钟直播剪成竖屏短视频只要 97 秒

一、我为什么盯着这个仓库

先说背景。我自己剪视频剪过一阵子，知道那个” 把长视频变成竖屏短视频” 这件事有多烦。

最烦的不是剪辑本身，是等待。你手里有个 85 分钟的直播录屏，扔到 OpusClip 这种云端服务上，它先要整段上传，然后服务端转码，然后跑一遍 ASR，然后跑一遍大模型分析，最后拼装导出。一个中等网速的宽带传 85 分钟 1080p 大概 1.5 GB，等上传就得十几分钟；转码又是几分钟；分析又是几分钟。等它终于吐出来三条竖屏片段，你可能已经不想剪了。

第二个烦点是钱。OpusClip 是订阅制加 credits 制，你剪得越多越贵。

第三个烦点是素材。你的直播录屏可能涉及别人的画面、别人的声音、别人的 ID。上传到第三方服务器这件事，对创作者来说不是纯技术问题。

然后我在 GitHub 上翻到 iamajmeena/neonclipping。2026 年 11 月 19 日创建，五天之后 2927 个 star、194 个 fork。作者是印度 Jaipur 的导演 Ajay K Meena，同时是调色师和 DaVinci Resolve 讲师 —— 也就是说这不是个纯工程师做的玩具，他自己就是那个被剪辑流程折磨的人。

我第一次读到 README 里的这句话：

Clip an 85-minute stream in 97 seconds, 100% locally, with zero API cost.

85 分钟，97 秒，零 API 费用，全本地。这几个数字放在一起太违反直觉了，我决定把源码拉下来看看到底怎么做到的。

它的自我定位是：

Paste a link. Get captioned 9:16 clips in about two minutes. Free, local, open-source.

支持 YouTube、Twitch、Kick 的链接，也支持你自己本地的 MP4。输出是 1080×1920 的竖屏片段，带烧录字幕、带标题、带开场 hook。

技术栈全在 README 的 Credits 段落里列明了：FFmpeg、yt-dlp、FastAPI、faster-whisper、OpenCV（YuNet 人脸检测，MIT）、Ollama。

架构上是一个本地 FastAPI 服务，README 里的”How it is built” 表格列了核心文件分工：

三、核心机制一：音频优先（这才是 97 秒的来源）

整个项目的核心设计决策只有一个，但它决定了一切：永远不要下载完整视频去分析。

Fast 模式（默认，视频超过 10 分钟就走这条路径）的流程在 README 里写得很清楚：

  1. 只下载音频（85 分钟视频 → 79 MB，大约 10 秒）
  2. 免费拿 transcript——YouTube 自己的字幕是逐词带时间戳的（json3 格式），不需要语音模型。其他源才用本地 Whisper 兜底
  3. 给整条音轨打分 —— 响度突变（对比 2 分钟局部基线）、人声抬升（2–4 kHz 能量）、安静到爆发的过渡
  4. 读候选段落的 transcript，交给本地 Ollama 打分、写标题和 hook，把起止点吸附到句子边界
  5. 只下载被选中的那几秒视频，按声音匹配精确裁剪，用 FFmpeg 渲染 1080×1920 并烧录字幕

关键在第 1 步和第 5 步。79 MB 的音频下载只要 10 秒；一个 85 分钟视频的完整 1080p 大约 1.5 GB，下载要几分钟。所以” 只下载音频做分析，只下载片段做渲染” 这一招直接把耗时从” 下载 + 转码 + 分析” 压缩成” 下载音频 + 分析 + 下载片段”。

这个思路不是我给它总结的，是作者自己在 README 的 Credits 里承认的：

Design ideas studied from open-source clippers: PeakCut (audio-first download, captions as transcript, section download)…

也就是说是抄了 PeakCut 的公开思路，代码自己重写。

3.2 字幕质量上，作者做了一个反直觉的决定

README 里有一段很值得读：

The local “Accurate (turbo)” model was removed because its captions were worse.

也就是说，作者试过本地语音模型，发现本地 Whisper 转出来的字幕比 YouTube 自动字幕还差，尤其是游戏语音场景。于是他把那个模型删了，只留一个”Best Hindi (large-v3, slow)”。

这跟很多人的直觉相反。我们默认” 本地模型 >= 云端自动字幕”，但这里字幕质量取决于源内容和模型能力对比，而不只是” 本地还是云端”。作者给了一个实测：

on a 2-hour Hindi stream a Make run took 197 s with correct lines like “poori mod di yaar, kya bhai? arre pulis”

同时他也诚实说 YouTube 自动字幕本身也不完美，尤其 Hinglish 混说的时候。

四、核心机制二：纯手写的信号打分（没有任何模型）

这是我觉得这个项目最值得学的地方。highlights.py 的文件头注释把设计说得很清楚：

Signals (all local, no model download):
motion - OpenCV Farneback optical flow at 160x90, 90th-percentile magnitude per second (fast objects, explosions, car flips); hard scene cuts are detected and excluded from motion, counted as cut density.
audio - loudness JUMP vs the local 2-minute baseline (sudden boom/shout beats constantly loud music).
shout - share of 2-4 kHz energy (voices raised, screams, impacts) weighted by loudness jump.
cuts - editing/camera-cut density.

全是不需要下载任何模型的信号处理。

4.1 Optical flow：运动量

它把视频缩到 160×90 的灰度，降到 3 FPS，然后用 cv2.calcOpticalFlowFarneback 算光流，取每帧位移幅度的 90 百分位数（不是最大值 —— 最大值会被单个噪点拉飞，90 分位更能代表” 大面积快速运动”）。

这里有个细节我觉得是整个 highlights.py 里最漂亮的一行：

硬切场景不参与运动量计算，而是单独计为 cut density。 原因很直白：一个从 A 场景硬切到 B 场景的画面，相邻两帧差异巨大，光流会爆表 —— 但那不是” 发生了什么激烈的事”，那是” 剪辑点”。不排除掉的话，每个剪辑点都会被误判成高潮。

三个要点：

五、核心机制三：本地 LLM 只读文字，且必须” 有据可依”

信号打出来的只是候选。真正决定选哪几条、标题怎么写的，是 smart.py 里的本地 LLM 调用。

这里的设计原则我觉得比实现本身更值得看。smart.py 的文件头就写死了：

Smart highlight refinement: shortlist by motion/audio, read each candidate’s transcript locally, let local Ollama score and title it. Falls back to the activity score when Ollama unavailable.

README 有一条很诚实的限制：

The LLM sees text only. It cannot see the screen.

这不是 bug，是有意的架构约束：让整个打分流程可以在纯 CPU 机器上跑。

六、核心机制四：自动找摄像头框（这是我最喜欢的一段）

主播的摄像头框在哪？很多剪辑工具让用户手动拖。NeonClipping 想自动找。

facecam_detect.py 的文件头把这个思路讲得非常清楚：

A streamer’s webcam is a rectangle whose border stays in exactly the same place in every frame (usually in a corner) and that contains a face. Game panels (minimap, HUD, chat) also have static straight borders, so the border alone is not enough:

  1. look at ~14 frames spread through the video,
  2. mark the pixels that carry an edge in (almost) every frame: static borders,
  3. list the best rectangles anchored at a corner whose two inner borders are static,
  4. run the small YuNet face detector (MIT licence, 230 KB, models/face_detection_yunet_2023mar.onnx) inside each candidate:
    the webcam is the candidate that holds a face in most frames; a minimap never does,
  5. if no bordered rectangle holds a face, look for a face that sits in the same spot in most frames (a borderless overlay).

关键洞察：小地图、HUD 面板、聊天框的边框也是静止的直线边框，光靠” 边框不动” 区分不出来。所以要再加一层人脸检测。

静态边缘的提取用累积频率：

thin 是” 在至少 75% 帧里都在的边缘”，thick 是膨胀一个像素的版本 —— 这样即使边框位置抖动一个像素也算数。这个细节很实在，实际视频里压缩噪声会让边框线轻微位移。

作者给的实测数据：

Measured on 30 real saved streams: found the webcam on every stream that has one; clean “not found” on trailers and talking-head videos. Not perfect: some boxes cover only the face inside a framed webcam.

还诚实承认了不足：有时候框出来的只是摄像头画面里的人脸区域，不含摄像头边框本身。

七、核心机制五：从” 听出来的高潮” 到” 说得好的段落”

前面几节讲的都是信号（响度、运动、音效）。但一个好的短视频不一定吵。

smart.py 里有一条 “Balanced” 模式会额外加入” 对话型候选”：

curation.transcript_candidates 的实现很有味道 —— 它在 transcript 里找” 叙事标记词”：

中英文印地语混排的关键词：but / actually / instead / why / how / because / wait / wrong / mistake / never / finally / imagine / secret / lekin / kyun / kaise / galti / pata / achanak。

这些词的共同点是：说话人在这里做了一个转折或者抛出一个问题。"wait, but actually..." 后面往往就是有意思的东西。再加上问号和感叹号的权重，以及 focus 匹配。

三种模式的权重差异在 curation.profile_weights：

Dialogue 模式把 LLM 权重从 2.5 提到 3.5，把 motion 从 .5 压到 .25。这就是” 少看热闹多听内容” 的量化表达。

7.1 句子边界吸附

选出来的片段不能硬切。smart.py 的 snap() 处理这个：

  • 开头：如果前 2.5 秒是静音，往后挪到人声真正开始
  • 结尾：尽量让句子说完（可以到 +8 秒），否则往前收到上一个句末
  • 绝不能断在 “and” / “matlab” 上（matlab 是印地语的” 就是”，断在这里非常尴尬）

7.2 去重与多样性

选片段时不能全是同一段。curation.select 做了三层过滤：

  1. 时间重叠超过 35% 的直接排除
  2. 词集合 Jaccard 相似度高要扣 0.20 分
  3. 同类型（都是 humour / 都是 story）连出要扣 0.08 分

Action 模式直接跳过第 2、3 步 —— 动作流就是要几个连续的爽点。

我自己的判断：

对比 OpusClip：这是最直接的对比。OpusClip 是这个赛道的标杆，做得也确实好。但云端意味着三件事 —— 上传时间、按量计费、素材出境。NeonClipping 的全部设计都指向” 把上传时间干掉”，音频优先这个招是最有效的。也正因为如此，它的能力边界也更清晰：只能剪 YouTube/Twitch/Kick 上能直接链接到的内容。

对比 PeakCut：作者在 Credits 里明说设计思路来自 PeakCut（audio-first download、captions as transcript、section download），连” 静态边框找人脸框” 的思路也是。区别在于 NeonClipping 的功能面宽得多 —— 直播实时剪辑、创作者自动监控、发布对接、MCP 接口、手机远程，全是 PeakCut 没有的。而且 PeakCut 是 MIT，NeonClipping 现在是 AGPL。

对比 OpenShorts / SupoClip / Reelsaw 这类自托管：它们多数是 Docker 化、面向服务器的，而且常常需要你提供 LLM API key。NeonClipping 明确”no Docker”，install.sh 直接跑，而且默认连一个模型都不用下载就能用纯信号打分。这一点对普通创作者友好得多。

对比传统剪辑软件（Premiere / Resolve）：完全不同的定位。NeonClipping 不做精细剪辑，它做的是” 从 85 分钟里挑出 3 个能发的片段”。它甚至还导出 Premiere Pro / DaVinci Resolve 的 XML 包，把工程交还给专业工具。

十一、真实局限（不吹的部分）

README 里有一个专门的 “Honest limits” 段落，作者难得地诚实。我把关键几条抄下来：

  • Highlight picking is a heuristic plus a small local LLM. It finds loud, energetic, quotable moments, not guaranteed “viral” ones. Review before posting.
  • The action cues (motion, flash, light flicker) are simple heuristics on a tiny low-resolution copy; they rank moments, they do not recognise “a police chase”. Star ratings are how it gets better at your taste.
  • The LLM sees text only. It cannot see the screen.
  • Without YouTube captions (Twitch VODs, uploaded files) a speech model must transcribe each candidate, which is slow on CPU.
  • Deep mode was verified on a short video only; on multi-hour videos it downloads the whole file first and is slow by design.
  • Live clipping: one live session at a time, and the computer must stay awake and online while it records.
  • Caption languages: … Captions are drawn with fonts installed on your computer, so scripts without a font may show empty boxes, and right-to-left languages (Arabic, Persian, Hebrew, Urdu) have basic support only.
  • Facecam presets are starting points, not detection: if you pick Bottom-right but the cam is bottom-left, the top half of the clip will show the wrong area.

我再加上我自己看源码和仓库得出的几点：

1. 项目非常新，只有 5 天大

创建于 2026-11-19，我拉代码时最新推送是 2026-11-24。56 个 open issue。README 里有多处 “not yet tested on a real Mac”：

Mac/Linux: install.sh (new, not yet tested on a real Mac).

以及：

the maintainer has not yet tried the Mac installer on his own Mac, so tell us if it misbehaves

2. 项目只有 200 个文件，但体量已经很大

我数了一下 git ls-tree -r 是 200 个文件，核心 Python 模块动辄几百行（app.py 1068 行、smart.py 313 行、facecam_detect.py 314 行、curation.py 大几百行）。这是一个功能面铺得很开、但单人维护的项目。README 提到作者的合作者只有他一个人（Instagram、邮件、GitHub issue 三种联系方式）。

3. AGPL-3.0 是个需要考虑的事

4. 需要 YouTube 访问畅通

作者自己写了一大节讲 “Sign in to confirm you’re not a bot”。共享网络、VPN、办公网、老下载器都可能触发。解决方案是升级 yt-dlp、换客户端模式重试、用浏览器 Cookie、换网络。他说：

Use a throw-away Google account if you do not want your main one attached to automated downloads.

5. 依赖 Python 版本上限

Python 3.10 to 3.13 (the newest Python often has no wheels for the speech/vision packages yet)

这不是小事。Python 3.14 出来之后你可能装不上。

6. 电竞解说类视频的字幕准确度

Hinglish 混说是公认的难题。README 承认：

Auto-caption accuracy follows the source: YouTube’s auto captions are imperfect, especially Hinglish.

7. “自动找摄像头框” 仍不是 100%

作者自己说：”some boxes cover only the face inside a framed webcam”。而且如果用户手动选了 “Bottom-right” 但摄像头实际在左下，那还是会错 —— 预设只是起点，不是检测结果。

十二、适合谁 / 不适合谁

适合

  • 游戏主播 / 直播创作者 —— 这是它的主场。聊天热度切片、摄像头自动识别、游戏音效识别（枪声 / 爆炸）全是为这个场景写的
  • 自己做自托管替代方案的人 —— 不想把素材传给别人，也不想按分钟付费
  • 有 NVIDIA 卡或至少一台还不错的机器的 Windows 用户 ——README 明确说 Mac/Linux 安装脚本作者自己还没在 Mac 上试过
  • 想给本地小模型攒数据的人 ——learn.py 里的五星评分 + 岭回归权重学习（往 DEFAULT 收缩）是个小而干净的偏好排序器实现
  • 想让 Agent 帮忙剪视频的人 —— 项目自带本地 MCP 接口

不适合

  • 完全不懂技术的创作者 —— 虽然有 .bat 一键装，但” 装 Ollama”” 拉 llama3.2:3b”” 确保 FFmpeg 在 PATH 上” 这几步对纯新手还是有门槛
  • 只剪精修长视频的人 —— 它不做调色、不做复杂转场、不做多机位。它做的是切片
  • 需要 4K 高保真输出的团队 ——README 说 4K 是 AV1/VP9，”much larger, slower to decode”，实测 20 秒片段 4K 要 70 MB
  • 想 fork 下来闭源商用的公司 ——AGPL-3.0 卡死这条路
  • 纯 Linux 无显卡的老机器 ——x264 CPU 编码 + Whisper CPU 识别会很慢，虽然能用

那 MCP 接口是怎么回事

README 有一段：

Start NeonClipping, then configure your MCP client with command uv and arguments run, --script, and the absolute path to neon_mcp.py. The stdio connector uses the local server on port 8770 (override with NEONCLIPPING_PORT). It provides create_clips, batch_status, resume_batch, list_clips, export_clip and download_clip.

提供 create_clips、batch_status、resume_batch、list_clips、export_clip、download_clip 六个工具。这是我最近见到的” 给 Agent 用的视频工具” 里比较完整的一个 —— 不是让 Agent 调 ffmpeg 参数，而是给它一个” 给我剪 3 条” 的高层接口。

十三、几个我觉得值得单独记住的技术点

最后我把看源码过程中觉得最值得学的几点拎出来。

1. “先小后大” 的分层数据获取

音频（79 MB）→ 视频片段（几 MB），而不是视频（1.5 GB）→ 片段。这个思路可以套用到任何” 从长内容里提取子集” 的场景。

2. 用局部基线代替全局基线

_z() 用 2 分钟滚动窗口算 z-score。噪声大但均值会漂的信号（直播音量、聊天热度），局部基线是标准做法。

3. 硬切排除在运动量之外

if mean(absdiff) > CUT: flow.append(0.); cuts.append(1.)—— 把” 剪辑造成的假信号” 和” 真实运动” 分开。这一行挽救了大量误判。

4. MAD 代替标准差

hits = flux > med + 6 * mad。MAD 对离群值不敏感，比 mean + 3 * std 稳健得多。

5. 生成内容必须可验证

hook 校验那三重检查（引用真实、语义支撑、数字一致）—— 这是我认为这个项目里最有产品思维的一段。AI 生成文案最大的风险是” 说得像真的但不是真的”，用代码把住这个口子，比在提示词里写十遍” 不要编造” 管用。

6. 位置偏差校正

倒序再读一遍取平均 —— 这是很多做 LLM-as-judge 的人会踩的坑，作者不但踩了还处理了。

7. 编码器要真跑一次才算数

works() 里那个 0.2 秒的测试编码。

十四、我接下来打算怎么用

说实话，看完源码我最大的感受不是” 这个项目做得真好”，而是它把”AI 剪辑” 这件事的工程边界划清楚了。

它没有试图让模型看懂视频。视频理解（识别” 这是一场追捕”）是另一个量级的难题，需要视频多模态模型、贵得多、慢得多。它的做法是：用便宜的确定性信号把 85 分钟缩到 20 个候选，再让便宜的小模型在文本上做选择和写作。这条流水线的每一步都是可解释、可调参、可离线运行的。

而且它诚实地把” 学到了你的口味” 这件事做成了一个小而干净的本地偏好学习器。learn.py 里：

11 个特征，8 条评分起步，岭回归往默认值收缩。这个规模刚好对应” 能记住你的偏好，但还没聪明到能自己判断”。

我会试的场景是：剪我自己录的技术分享长视频。因为技术分享的” 精彩瞬间” 往往不是喊叫，而是一句” 所以问题就在这儿”—— 这正好是 Dialogue 模式加 transcript 候选那套逻辑擅长的。

我也会用 MCP 接口接进我的 Agent 工作流，让它在我录完之后自动产出候选片段。

最后一句提醒：这个项目 5 天大，AGPL 刚换，Mac 安装没在作者自己的 Mac 上试过。如果你要用在正式工作流里，先小规模试，别一上来就依赖它。
