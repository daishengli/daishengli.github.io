jingyaogong/minimind：7 万 star 的中文极简 LLM 教学项目，2 小时 3 块钱从零训出 64M 大模型

发表于 2026-11-27 分类于 开源项目
jingyaogong/minimind 是 GitHub 上最受欢迎的中文从零训练 LLM 教学项目之一，累计 71615 个 star、9298 个 fork，Apache-2.0 协议，纯 Python 实现，2024 年 7 月建仓至今保持高频提交。它用原生 PyTorch 把大语言模型从零到一的完整链路全部摊开，涵盖 Tokenizer 训练、预训练、监督微调、LoRA、知识蒸馏、DPO、PPO、GRPO、CISPO、Agentic RL、Tool Use、自适应思考等环节，目标是让个人开发者用单卡 RTX 3090 在约 2 小时、3 元人民币内复现一个 64M 参数的对话模型。主线 minimind-3 结构对齐 Qwen3 生态，Pre-Norm 加 RMSNorm、SwiGLU 激活、RoPE 加 YaRN 外推、q_heads 8 与 kv_heads 4、词表仅 6400、8 层 768 维；MoE 版本 minimind-3-moe 为 198M-A64M、4 专家 top-1 路由。兼容 transformers、trl、peft 训练框架与 llama.cpp、vllm、ollama、sglang 推理引擎，开源全阶段中文数据集、OpenAI 协议兼容 API 服务端与 Streamlit WebUI，并附 C-Eval、C-MMLU、ARC-Easy 等第三方测评结果，README 主动披露了评测标准误与数据污染对照，诚实标注工具调用泛化不足、奖励稀疏等真实局限。

jingyaogong/minimind：7 万 star 的中文极简 LLM 教学项目，2 小时 3 块钱从零训出 64M 大模型

一、我被一句”3 块钱” 骗进去了

去年我朋友给我发了个链接，附一句话：” 你花 3 块钱就能训一个大模型。”

我当时的反应是典型的技术人反应 —— 觉得这是个标题党。3 块钱，按现在租卡的行情连一小时 3090 都买不到一半，更别提” 训一个模型” 这四个字。我以为又是拿 LoRA 微调 Qwen 假装” 从零训练” 的那种把戏，正准备回一句” 又在骗小白”，他补了一句：

“真的是从 0 开始训，64M 参数，两小时。”

我点进去看了眼仓库首页，jingyaogong/minimind，7 万 star，Apache-2.0。

然后我花了整整一个周末把它跑通了。跑完之后的结论比” 标题党” 复杂得多：这个项目确实是个标题党 —— 它的 README 确实用”3 块钱” 这种最夸张的方式宣传；但它宣传的那个东西，也是真的。这篇文章我想认真写一下 MiniMind 到底做了什么、怎么做的，以及它真正适合谁、又有哪些坑。

二、它想解决什么问题，以及它是什么

2.1 从” 用模型” 到” 造模型” 的断层

现在的大模型教程，主流形态是什么？打开任意一个热门仓库，你看到的是这样的代码：

十几行，全流程跑通。方便是真方便，但问题也在这里：你并没有看到大模型是怎么运转的。

transformers 把 RoPE 旋转位置编码、KV Cache 的组织方式、Pre-Norm 的残差流向全包在 LlamaAttention 这个类里；trl 把 PPO 的四模型协同、优势估计、KL 惩罚塞进一个 PPOTrainer；peft 把 LoRA 的低秩分解藏在 get_peft_model() 后面。

你可能会说” 我不需要重造轮子”。但作者在 README 里的观点很直接：

“绝大多数探索最终都止步于使用 LoRA 等技术对现有大模型做少量微调…… 这更像是在教牛顿如何使用 21 世纪的智能手机 —— 虽然有趣，却偏离了理解物理本质的初衷。”

我觉得这个比喻有点用力过猛，但它指出的问题是真的：用框架做微调，学到的是” 怎么调参”；用框架从零训练，学到的是” 怎么造”。

2.2 另一个被忽视的现实：训练成本

想学 LLM 的人很多，但真能动手训练的不多。为什么？

不是不想，是试错成本太高。你写完 300 行训练脚本，租一张 A100 跑两小时，出来一个 loss 曲线看不懂的 checkpoint，你根本不知道是自己的实现有 bug，还是超参没调好，还是数据有问题。

跑一次全流程实验的成本，够你买好几本 O’Reilly 的书。

MiniMind 的整个设计哲学就是围绕这一点：把每次实验的成本压到可以忽略不计。

模型小到 64M，单卡 3090 就能训；数据小到 1.2GB 起步，mini 数据集下载完就能跑；训练时间短到 1-2 小时；成本低到 3 元人民币级别。

这不是炫技的极简主义，而是教学工程学：让学习者能在一天之内完成” 读代码 → 改代码 → 跑起来 → 看结果 → 理解原理” 的完整闭环。

2.3 第三个动机：让中文社区有一份自己的实现

README 里提到作者对市面上” 付费课程和营销内容” 的批评，并感谢了 karpathy/llama2.c 这类项目。中文圈此前有 build_MiniLLM_from_scratch、baby-llama2-chinese、tiny-llm-zh 等不少从零实现的项目，但它们大多停留在” 能跑通一个简化版 Transformer” 的阶段，没有把后训练（RLHF / RLAIF）和 Agentic RL 这条线补齐。MiniMind 的野心是把从 tokenizer 训练到 Agentic RL 的整条链路都铺出来，而且每一步都从 0 写。

2.4 一句话定义 + 关键数字

先给结论：

MiniMind 是一套用纯 PyTorch 从 0 实现的、覆盖大语言模型全生命周期训练流程的中文教学级开源项目，主线模型 64M 参数，单卡 3090 约 2 小时、3 元人民币即可从零训练出一个可对话的模型。

三、核心结构：它长什么样

3.1 minimind-3 的架构参数

minimind-3 Dense 使用 Transformer Decoder-Only 结构，配置刻意向 Qwen3 生态对齐，方便后续转到 transformers / llama.cpp / ollama / vllm：预标准化（Pre-Norm）+ RMSNorm、SwiGLU 激活函数、RoPE 旋转位置编码（支持 YaRN 外推）、q_heads=8 / kv_heads=4（GQA）、max_position_embeddings=32768、rope_theta=1e6。

各版本配置对照表（README 原表）：

Model Name params len_vocab max_pos rope_theta n_layers d_model kv_heads q_heads note
minimind-3 64M 6400 32768 1e6 8 768 4 8 Dense
minimind-3-moe 198M-A64M 6400 32768 1e6 8 768 4 8 4 experts / top-1
minimind2 104M 6400 32768 1e6 16 768 2 8 历史版本

模型配置在 ./model/model_minimind.py 里改，很好找。

3.2 为什么是 8 层 768 维

这一段是 README 里我觉得最有价值的部分，作者引用了 MobileLLM 的系统性研究来解释小模型的参数分配。

Scaling Law 在大模型上强调数据量、参数量、训练步数的决定性作用，架构差异的影响会被弱化。但在小模型区间，这个结论不总是成立。

MobileLLM 的核心观察是：参数量固定时，深度往往比宽度更重要。在参数量固定在 125M 或 350M 时，30~42 层的” 瘦高个” 结构通常优于 12 层左右的” 矮胖子”，在常识推理、问答、阅读理解等多个基准上趋势一致。

但” 窄” 也有下限：d_model < 512 时，词嵌入维度过窄的劣势会明显放大，堆层数不足以弥补固定 q_head 下 d_head 偏小的问题；d_model > 1536 时，继续加层数比单纯加宽更划算。

所以 MiniMind-3 选 dim=768, n_layers=8：更浅的网络训练更快，同时 dim 不至于过小导致模式崩溃。作者的说法是” 在训练效率、稳定性与最终效果之间取得相对均衡”。

这个取舍是通用的。 你以后自己做小模型，这个结论可以直接抄。

3.3 MoE 的现实主义版本

minimind-3-moe 在同一结构上扩展 MoE 前馈层，兼容 Qwen3-MoE 风格配置，去掉了 shared expert。

默认配置是 4 experts / top-1 routing，用更低的激活参数换更高的容量。

但作者对 MoE 的性能表现很坦诚，这段话我觉得比任何吹捧都值钱：

“Experts 继续增加后，实际耗时往往比同尺寸规模的 dense 模型高非常多，这和 ‘MoE 推理更快’ 放在一起看会有点反直觉，但训练时 token 先按专家分桶、再分别做 forward，原生训练时带来的 kernel 启停和调度开销会急剧变重…… 得靠支持 MoE kernel-fused 的算子库来优化，比如基于 Triton 的自定义 kernel、DeepSpeed-MoE、Megatron-LM 等等。当然，这个项目还是希望保留原生 PyTorch 的普适性，所以这里做的是现实的折中，在当前实现下，4 experts / top-1 这个甜点配置大约只比 dense 模型慢 50% 左右。”

翻译一下：MoE 省的是参数，不是算力。 在没有 kernel 优化的纯 PyTorch 实现里，MoE 的实际训练成本比同规模 dense 更高。实测数据也印证了这点：

Model Name params pretrain_t2t_mini sft_t2t_mini toolcall RLAIF
minimind-3 64M ≈1.21h / ≈1.57￥ ≈1.10h / ≈1.43￥ ≈0.9h / ≈1.17￥ ≈1.1h / ≈1.43￥
minimind-3-moe 198M-A64M ≈1.69h / ≈2.20￥ ≈1.54h / ≈2.00￥ ≈1.26h / ≈1.64￥ ≈1.54h / ≈2.00￥

3.4 Tokenizer：6400 这个数字很关键

MiniMind 的词表只有 6400，对比一下业界：

Tokenizer 词表大小
Yi / Qwen2 / ChatGLM 64,000 / 151,643 / 151,329
Mistral / Llama 3 32,000 / 128,000
MiniMind 6,400（自定义）

为什么这么小？因为对 MiniMind 这种百 M 级模型来说，词表大小直接决定 embedding 层和输出层的参数占比。

粗算一下：6400 × 768 × 2（embedding + output head）≈ 9.8M 参数，占 64M 总量的 15%。如果换成 151,643 的 Qwen2 词表，同样是 768 维，光 embedding + output 就是 233M 参数 —— 直接超过模型主体。也就是说，小模型选大词表，等于把参数预算全砸在查字典上了。

代价也很明确。作者自己写：

“尽管 minimind_tokenizer 的词表只有 6400，编解码效率弱于 qwen2、glm 等更偏中文友好的 tokenizer，但它能显著压缩 embedding 层和输出层的参数占比，更适合 MiniMind 这类小模型的体积约束。从实际使用效果看，这套 tokenizer 并没有明显带来生僻词解码失败的问题，整体仍然足够稳定可用。”

还有一个容易被忽略的点：tokenizer 会影响 PPL 这类按 token 统计的指标。跨 tokenizer 比较时，BPB（Bits Per Byte）往往更有参考价值。所以拿 MiniMind 的 PPL 去和 Qwen 的 PPL 比，是没有意义的。

作者也建议不要重新训练 tokenizer：

“不建议重新训练 tokenizer，因为词表和切分规则一旦变化，模型权重、数据格式、推理接口与社区生态的兼容性都会下降，也会削弱模型的传播性。”

顺带一提 MiniMind tokenizer 在中文上的压缩比：大约 1.5~1.7 字符 /token，纯英文约 4~5 字符 /token。

四、训练流程：从预训练到 Agentic RL

这是 MiniMind 最核心的部分。整条链路是：

每个环节都有独立脚本，都在 trainer/ 目录下执行。

4.1 预训练：学” 高质量词语接龙”

README 对预训练的描述很形象：

“更直白地说，模型在这一阶段的核心目标就是学会高质量地词语接龙。例如输入” 秦始皇”，它要能够继续生成” 是中国历史上的第一位皇帝” 这类符合语义与常识的后续内容。”

命令是 python train_pretrain.py（或 torchrun --nproc_per_node 1 train_pretrain.py），输出 out/pretrain_*.pth（* 是模型 dimension，默认 768）。

4.2 SFT：把模型掰成” 会对话” 的样子

SFT 阶段让模型适应当前仓库使用的多轮对话模板，理解 user / assistant / system / tool 等角色结构。命令是 python train_full_sft.py，输出 out/full_sft_*.pth。

这里有个容易被低估的点，作者专门展开讲了：

“SFT 并不只是把模型调成’更会聊天’…… 尤其是像 MiniMind 当前主线这样体量达到 14GB 的 SFT 数据，本身就已经不只是简单的格式对齐，而更接近一种带有 mid training 性质的持续强化过程。”

换句话说，当 SFT 数据的体量和多样性足够大时，SFT 本身就是 mid-training。这个观点和 Meta 在 Llama 3 里的做法是一致的 —— 中期训练数据占整个预训练 token 的大部分。

4.3 断点续训：训练中断不再从头再来

所有训练脚本都支持 --from_resume 1：

具体行为：检查点自动保存在 ./checkpoints/，命名 <权重名>_<维度>_resume.pth（如 full_sft_512_resume.pth）；支持跨不同 GPU 数量恢复（自动调整 step）；支持 wandb 训练记录连续性（自动恢复同一个 run）。

这个功能听起来平淡，但在你租卡的时候断了，才知道它多重要。

4.5 知识蒸馏：黑盒 vs 白盒

这个分类我觉得是全篇 README 里概念最清楚的一段。

黑盒蒸馏：本质上仍然是面向教师输出结果的监督微调，也就是基于硬标签继续训练。学生模型只能看到” 老师说了什么”，看不到老师内部怎么判断。DeepSeek R1、Qwen3 的高质量回答，以及 tool call、reasoning、思维链数据，都属于这一类。

$$\mathcal{L}{blackbox} = \mathrm{CE}(y{teacher}, p_{student})$$

白盒蒸馏：额外学习教师在 token 分布层面的偏好，学生学到的不只是” 标准答案”，还包括教师在候选 token 之间的相对倾向。

$$\mathcal{L}{whitebox} = \alpha \mathcal{L}{CE} + (1-\alpha) T^2 \mathrm{KL}(p_t^T \parallel p_s^T)$$

对应脚本 train_distillation.py，实现里包含教师 / 学生双模型加载、CE + KL 混合损失、温度缩放、MoE 与 dense 组合蒸馏、断点续训和分布式训练。用 python train_distillation.py 启动。

4.7 强化学习：PO 算法的统一视角

这是整个项目技术含量最高的部分，也是我读得最慢的一段。作者先给了一个统一框架 —— 所有 Policy Optimization 算法本质上都在优化同一个期望：

$$\mathcal{J}{PO} = \mathbb{E}{q \sim P (Q),, o \sim \pi_\theta (\cdot \mid q)} \left [ \underbrace {\Phi (r_t, A_t)}_{\text {策略目标}} - \underbrace {h (\text {KL}t)}{\text {正则项}} \right]$$

三个核心组件：策略项 $\Phi (r_t, A_t)$（如何结合概率比和优势更新策略）、优势项 $A_t$（如何计算优势）、正则项 $h (\text {KL}_t)$（如何约束变化幅度）。

作者的原话很妙：

“大模型算对定积分也不足为奇，小模型回答对加减法优势通常都是正的。”

意思是：优势估计的难度与模型能力正相关，模型越强，优势信号越容易算出来。

DPO 的损失：

$$\mathcal{L}{DPO} = -\mathbb{E}\left[\log \sigma\left(\beta \left[\log \frac{\pi\theta(y_w|x)}{\pi_{ref}(y_w|x)} - \log \frac{\pi_\theta(y_l|x)}{\pi_{ref}(y_l|x)}\right]\right)\right]$$

策略项是 $f (r_t) = \log r_w - \log r_l$，无显式优势项，KL 约束隐含在 $\beta$ 中。

DPO 从 PPO 带 KL 约束的目标推导出对偏好对的解析训练目标，无需同步训练 Reward/Value 模型，只需 actor 与 ref 两个模型，显存占用低、收敛稳定、实现简单。范式是 off-policy，使用静态偏好数据集，可反复多轮 epoch。

PPO 的损失里，策略项是 $\min (r_t \cdot A_t, \text {clip}(r_t, 1-\varepsilon, 1+\varepsilon) \cdot A_t)$，优势项由 Critic 网络估计（或用 GAE 计算），正则项是全局 KL 约束。

GRPO 的损失：

$$\mathcal{L}_{GRPO} = -\mathbb{E}\left[\min(r_t \cdot A_t, \mathrm{clip}(r_t, 1-\varepsilon, 1+\varepsilon) \cdot A_t) - \beta \cdot \text{KL}_t\right]$$

GRPO 的核心创新是” 分组相对价值估计”：对同一个问题生成 N 个回答，用组内平均奖励作 baseline，不需要额外训练 critic 网络。

优势项：$g (A_{i,j}) = \frac {R_{i,j} - \mu_i}{\sigma_i + \epsilon}$

CISPO 的损失：

$$\mathcal{L}{CISPO} = -\mathbb{E}\left[\min(r_t, \varepsilon{\mathrm{high}}) \cdot A_t \cdot \log \pi_\theta(a_t|s) - \beta \cdot \text{KL}_t\right]$$

CISPO 抓住的是 PPO/GRPO 里一个长期让人别扭的问题 ——ratio 被 clip 之后，梯度流直接被硬截断了。它把策略项改写成” 裁剪权重 × log 概率”，这样 ratio 即使被截断也不会把梯度路径一起截断。

实现上不用单开脚本，在 train_grpo.py 里把 loss_type 配成 cispo 就行。

作者的总结表：

算法 优势项 $g (A_t)$ 正则项 $h (\text {KL}_t)$ 训练模型数
DPO 无显式优势项 隐含在 $\beta$ 中 1（前向参与 2）
PPO $A_t$（Critic 估计 / GAE） $\beta \cdot \mathbb{E}[\text{KL}]$ 2
GRPO $A_{i,j}=\frac{R_{i,j}-\mu_i}{\sigma_i+\epsilon}$ $\beta \cdot \text{KL}_t$ 1
CISPO $\frac{R - \mu}{\sigma}$ $\beta \cdot \text{KL}_t$ 1

4.8 Agentic RL：仓库里最有意思的脚本

2026-03 起新增 train_agent.py，支持多轮 Tool-Use 的 online RL。

数据多了一个 gt 字段作为最终校验目标。训练时优化的对象不再是单轮回答 $y$，而是一条多轮轨迹：

$$\tau = (a_1, o_1, a_2, o_2, \dots, a_T), \quad a_t \sim \pi_\theta(\cdot \mid s_t, \mathcal{T})$$

如果某一步生成了 tool_call，就执行工具、把 observation 拼回上下文，再继续 rollout。奖励是对整条轨迹联合打分：

$$R(\tau) = R_{\text{answer}} + R_{\text{tool}} + R_{\text{format}} + R_{\text{rm}} - R_{\text{unfinished}}$$

同时考虑工具调用合法性、gt 命中、格式闭合、未完成惩罚与 Reward Model 分数。

作者对 rollout_engine（训推分离）的定位很清楚：

“当前实现仍是同步模式（采样完一批再更新），还不是纯 rollout buffer 的异步训练。”

并自评这套实现” 已经具备 openrlhf/verl/slime 等大规模 RL 框架的味道”，但” 还远不是工业级 Agent 训练框架”。

七、关键设计取舍

我把 MiniMind 里几个有代表性的取舍单独拎出来说说，因为这些思路比代码本身更值得学。

7.1 取舍一：原生 PyTorch vs 高层抽象

决策：全部从 0 手写，不依赖第三方框架的高层接口。

代价是真实的：LoRA 不走 peft、DPO 不走 trl、PPO 不走 openrlhf。分布式训练细节、梯度累积、学习率调度、checkpoint 管理都得自己处理。

收益也是真实的：每一行代码你都能解释。当你的 PPO 训崩了，你知道是 advantage 归一化写错了，不是某个库的默认超参不对。

对于一个教学项目，这个取舍无可争议 —— 但要注意它不适合直接搬到生产环境。

7.2 取舍二：MoE 的” 现实主义” 路线

README 里有一句话我很喜欢：

“当然，这个项目还是希望保留原生 PyTorch 的普适性，所以这里做的是现实的折中。”

明确知道当前实现不是最优（MoE 训练比 dense 慢 50%），明确知道最优解需要 Triton kernel、DeepSpeed-MoE、Megatron-LM，但仍然选择保留普适性 —— 因为对一个要被人读懂的教学项目来说，可读性 > 极限性能。

7.3 取舍三：奖励稀疏问题的工程解法

这是我认为整个项目技术含量最高的洞察。

MiniMind 这种 0.1B 参数量、能力较弱的模型，在 R1 风格的数学数据集上会遇到严重的奖励稀疏问题：

  • 现象：模型生成的候选回答几乎全部错误，所有奖励分数 $r (x,y) \approx 0$
  • 后果：优势函数 $A (x,y) = r (x,y) - b (x) \approx 0$，策略梯度信号消失

作者的类比：

“如同让小学生做高考数学题，无论尝试多少次都得零分，无法通过分数差异学习改进策略。”

解法是放弃二元奖励，改用连续奖励：Reward Model 输出连续分数（如 -2.5 到 +3.0）而非二元的 0/1，即使回答质量都差，仍能区分” 更差”(-3.0) 和” 没那么差”(-2.8)。稠密且连续的奖励信号能为优势函数提供非零梯度。

以及监控建议：

“监控训练时观察奖励分数的方差 $\text {Var}(r)$，若持续接近 0 则需调整数据或奖励机制。”

这行字比整篇 RL 公式都值钱。 大多数人跑 RL 训不出来，就是卡在这里但不知道为什么。

另外还有一个混合奖励的形式：

$$r_{\text{total}} = \alpha \cdot r_{\text{model}} + \beta \cdot r_{\text{rule}}$$

7.4 取舍四：GRPO 的退化组问题

GRPO 用组内平均奖励作 baseline，但这带来一个问题：如果某个问题上 N 个回答的奖励几乎一样，这一组的学习信号就接近 0。

作者明确指出：

“在 MiniMind 这种超小模型上，这个问题尤其明显，所以训练必须限制在合理的能力边界内。”

也就是说，你不能用 64M 的模型去解它根本解不出来的题。这是物理限制，不是算法 bug。

llama2.c 是最常被拿来对比的项目，也是 MiniMind 致谢列表里的第一位。

  • llama2.c：极致精简，用纯 C 实现 Transformer 前向推理，没有训练、没有后训练。它的价值是” 让你在几百行代码里看懂 transformer 前向传播”。
  • MiniMind：Python + PyTorch，覆盖从 tokenizer 到 Agentic RL 的完整训练链路。

选哪个取决于你的目标：想读懂前向传播用 llama2.c；想跑通全流程训练用 MiniMind。

9.2 MiniMind vs baby-llama2-chinese / chatlm-mini-chinese

这两个是中文小模型的经典对照对象，MiniMind 在 README 里拿它们做了直接横评。

  • baby-llama2-chinese（0.2B）：更早的教程型项目，在本次评测里垫底（21 分）。
  • chatlm-mini-chinese（0.2B）：知识准确性最高（准确性 25/30，远超 MiniMind 的 10/30），但代码能力是明显短板，且生成后段容易重复退化。

这个对比揭示了小模型的一个本质矛盾：在有限的参数预算下，” 说得好” 和” 说得对” 往往很难兼得。MiniMind 选了” 结构清晰 + 代码可用” 这条线，chatlm-mini 选了” 知识储备” 这条线。

9.3 MiniMind vs 其他中文小模型教程

  • build_MiniLLM_from_scratch：结构更简单，聚焦” 从零写 Transformer”。
  • tiny-llm-zh：更聚焦中文预训练语料的构建，数据工程做得更细。MiniMind 的数据策略是” 直接开源整理好的全阶段数据集 + 明确的来源标注”，省掉用户的数据预处理工作 —— 从” 降低入门门槛” 的角度 MiniMind 更彻底，但从” 数据质量研究” 的角度 tiny-llm-zh 值得单独看。
  • TinyLlama（Meta）：模型更大（1.1B），有正式的训练论文和数据配方，不是教学玩具。
  • SmolLM2-135M（HuggingFace）：有正式的训练论文和 benchmark，训练成本高得多。

MiniMind 的独特位置是：中文 + 全阶段 + 极低成本 + 从 0 实现。四个条件同时满足的，目前基本只有它。

9.4 MiniMind vs 工业级 RL 框架（openrlhf /verl/slime）

MiniMind 里的 train_agent.py 具备了这些框架的关键元素 —— 模板组织、工具执行、多轮 rollout、延迟奖励、训推分离 —— 但作者自己说是” 最小串联”，” 还远不是工业级 Agent 训练框架”。

维度 MiniMind verl / openrlhf
rollout 同步（采样完一批再更新） 异步 rollout buffer
训推分离 支持 sglang，但同步 完整异步 + 权重同步
资源调度 单机多卡 集群级
工程完备度 教学级 生产级

作者说” 如果类比到更大规模系统里，它其实已经具备 openrlhf/verl/slime 等大规模 RL 框架的味道”，我觉得这个措辞是准确的 —— 味道有了，骨架还是差挺远。

十、真实局限：作者自己承认的和我自己踩到的

这部分我尽量写全，免得你抄了之后才发现。

10.1 作者明确承认的

（1）知识幻觉严重。 这个没法回避。64M 参数的模型，事实性知识基本靠猜。README 里的评测显示 A 模型准确性只有 10/30—— 客观说基本是随机猜的水平（多选题随机作答的准确率往往就是很强的下界）。

（2）Tool Call 泛化能力不足。

“工具列表也主要覆盖约 10 个模拟的自定义工具…… 因此目前还谈不上明确的泛化能力。”

（3）Tool Call 与思考链无法同时稳定输出。

“当前同时开启 Tool Call 与显式思考时，模型通常并不太会稳定地输出思考过程。”

（4）奖励稀疏。 在通用数学任务上，64M 模型几乎全错，优势信号归零，RL 训不动。作者的解法（连续奖励）只能缓解，不能根除。

（5）GRPO 退化组。 小模型在难题上组内奖励趋于一致，学习信号消失。

（6）MoE 训练比 dense 慢。 4 experts /top-1 也要慢约 50%，专家更多则 kernel 调度开销急剧变重。

（7）Agentic RL 是同步模式。

“当前实现仍是同步模式（采样完一批再更新），还不是纯 rollout buffer 的异步训练。”

（8）只保证主线权重的维护。

“并非所有训练阶段或实验分支（如 DPO、PPO、GRPO、CISPO、Agent、LoRA 等）的权重都会持续维护并单独公开。”

（9）后训练有对齐税。 RL 权重在 ToolUse 上更强，但事实性下降、幻觉更明显。

10.2 我自己踩到的坑

（1）依赖版本。 老版本 transformers 的 apply_chat_template 可能不支持自定义模板，建议直接用较新的版本。

（2）显存。 README 里没说清楚不同阶段的显存需求差异。pretrain 阶段最敏感，因为 max_seq_len 直接影响激活值显存。只有 12G 卡的话，max_seq_len=768 可能会 OOM，需要降到 512 或 384。

（3）数据下载。 sft_t2t.jsonl 有 14GB，pretrain_t2t.jsonl 有 10GB。只是” 跑通看看” 的话用 _mini 版本（1.2GB + 1.6GB）就够了 —— 我第一次直接下了全量，等下载花的时间比训练还长。

（4）eval_llm.py --load_from 的两种语义。 --load_from ./minimind-3（transformers 格式目录）和 --load_from ./model --weight full_sft（torch 权重目录）是两条完全不同的路径，别混用。

（5）WebUI 需要先复制模型目录。 README 里特别标注了：

“⚠️ 须先将 transformers 格式模型文件夹复制到 ./scripts/ 目录下…… 如不存在则报错”

这个报错信息不直观，容易卡住。

（6）llama.cpp 转换要改代码（动 convert_hf_to_gguf.py），Ollama 需要手写 modelfile（模板较长，要完整复制 README 里的 TEMPLATE 部分）。

10.3 最重要的一条局限

这不是一个能用的模型，这是一个用来理解模型的教具。

如果你要的是” 能干活的中文小模型”，请去看 Qwen3-0.6B、Qwen3-1.7B，或者 MiniMind 系列的衍生项目 MiniMind-V（视觉）、MiniMind-O（多模态）。64M 的模型连” 万有引力是谁提出的” 都会答成爱因斯坦，它的存在意义不在于好用。它的价值在于：你可以在一个晚上读完整个训练栈，然后改任意一行代码看会发生什么。

十一、适合谁 / 不适合谁

12.1 适合

（1）想真正搞懂 LLM 训练全流程的人。 你已经会写 Python，知道什么是梯度下降和交叉熵 loss，但没搞明白为什么 SFT 之后还要跑 RL、PPO 和 GRPO 差在哪、DPO 为什么要冻结一个 ref 模型。这个项目能给你答案。

（2）想低成本做 LLM 实验的人。 你有 12G 以上的显卡，想试试” 改一下数据配比会怎样”” 换一种奖励函数会怎样”。3 块钱一次实验的成本，让你敢做对照组。

（3）中文开发者。 README、代码注释、数据说明全是中文，训练数据以中文为主。英文教程多，但中文的少。

（4）想给小模型做垂域适配的人。 LoRA 那套流程（准备 jsonl → 训 → 合并 → 部署）可以直接用在你自己的 7B/1.5B 模型上。

（5）要做 AI 教学 / 培训的人。 代码结构清晰、注释详实、每个阶段都有 loss 曲线和数据格式说明，比自己搭一套 demo 靠谱得多。

（6）想对比不同 RL 算法的人。 DPO / PPO / GRPO / CISPO 在同一套代码里实现，消融对比方便。

12.2 不适合

（1）想直接拿去用的。 64M 的知识准确率是随机猜水平，任何生产用途都不合适。

（2）想学最前沿架构的。 主线结构是对齐 Qwen3 的常规 Dense + MoE，没有 Mamba、没有 SSM、没有新的注意力变体。想看前沿的话，Discussions 里那两个实验性项目（dLM 扩散语言模型、Linear Attention）才有意思，但那是讨论区内容，不是主线。

（3）工程要求极高的。 没有完整的 CI、没有完善的测试覆盖、没有版本化的配置管理，checkpoint 管理是脚本级的。DDP 是原生 PyTorch 写的，没做 ZeRO、没做 offload、没做 pipeline 并行，数据加载是最朴素的 jsonl 读取。

（4）显存紧张的。 虽然宣称单卡 3090（24G）能跑，但 12G 卡需要调小 max_seq_len，效果会打折。纯 CPU 也能跑，但”2 小时” 这个数字就完全不存在了。

（5）想要开箱即用生产部署的。 OpenAI API 服务端是为了 demo 和教学写的，不是高并发服务。

（6）指望一个项目吃透所有东西的。 仓库里塞了 Pretrain、SFT、LoRA、蒸馏、DPO、PPO、GRPO、CISPO、Agentic RL、YaRN、Tool Use、自适应思考十几个主题，每个都只讲了个大概。它是地图，不是教材。

十二、我的实际使用建议

第一天：跑通最小闭环。 克隆仓库、装依赖，下载 pretrain_t2t_mini.jsonl（1.2GB）和 sft_t2t_mini.jsonl（1.6GB）放进 ./dataset/，然后：

用 mini 数据 + max_seq_len≈768，单卡 3090 大约 2.3 小时。这一步的意义是：你亲眼看到 loss 从 8 降到 2 附近，这个体感比读十篇教程都强。

第二天：读代码。 重点读三个文件：model/model_minimind.py（结构和配置）、trainer/train_pretrain.py（训练循环和数据读取）、trainer/train_grpo.py（RL 的采样、奖励、优势计算）。

第三天：做实验。 把 n_layers 从 8 改成 4，看训练速度和质量怎么变（验证 MobileLLM 的深度结论）；换个奖励函数，看 GRPO 的 reward 曲线怎么动。

第四天：接生态。 把模型转成 GGUF，扔进 llama.cpp 或 ollama 里跑 —— 这一步会帮你理解” 模型文件里到底存了什么”。

十三、写在最后

MiniMind 最让我佩服的不是 7 万 star，也不是那个”3 块钱” 的数字，而是它对” 我到底学会了什么” 这个问题的诚实。

README 里有太多这样的句子：” 目前还谈不上明确的泛化能力”” 同时开启 Tool Call 与显式思考时，模型通常并不太会稳定地输出思考过程”” 在 MiniMind 这种超小模型上，这个问题尤其明显”” 还远不是工业级 Agent 训练框架”” 上述对比仅为体验参考，非严格 benchmark”。

这种诚实，在开源项目里其实相当罕见。更重要的是，它主动公开了自己” 作弊” 能跑多少分：

“例如 minimind-3 在有污染的 ceval /cmmlu 子集上实验跑到过约 97% 准确率，但这种结果没有参考意义。”

一个愿意告诉你” 我在有数据泄漏的情况下能刷到 97%” 的项目，它的 24.89 分才有意义。

至于那个”3 块钱”—— 我跑了之后想说，它基本属实，但有点标题党的成分。README 里自己也澄清了：

“注：本项目基于 Apache 2.0 协议开源，完全免费。’2 小时’ 指 SFT 阶段在单张 NVIDIA 3090 上跑完 1 epoch 的实测耗时，’3 块钱’ 指对应时段的 GPU 租用成本。”
注意是 SFT 阶段 1 epoch，不含预训练；但合计约 2.31 小时、3.0 元的表格数据确实在 README 里写着。

所以结论是：这个项目值得你花一个周末。

不是为了训出一个能用的模型 —— 那不可能。而是为了在一个可控的尺度上，把大语言模型这件事从头到尾看一遍。
