一、先说个让我脸红的场景

去年我接了一个活：把公司一个跑了七八年的 Node.js 后端服务” 现代化”。老板的原话是” 用 Rust 重写一下，性能好”。我当时觉得这活儿挺简单 ——AI 都能写 Rust，我让它写不就行了？

于是我打开 Claude Code，说：” 把 src/ 目录重写成 Rust。” 一小时后它给了我一个 Cargo.toml、一堆 .rs 文件，和一句” 完成了”。

我跑了一下 npm test。138 个用例，挂了 71 个。

挂得五花八门：JS 的 slice 按 UTF-16 码元切，Rust 的 str 按字节切，一个 emoji 就切出乱码；JS 的 Math.round(-2.5) 是 -2，Rust 的 f64::round 是 -3（远离零）；JSON 序列化以后 key 顺序不一样；有几处异常类型都变了。

最难受的是我没法判断哪些是” 实现得不好”，哪些是” 本来就该不一样”。这才是真正的痛点：Rust 重写最大的成本不是写 Rust，而是证明它跟原来那个一模一样。

我后来自己写了一堆测试兜底，但写测试的过程比重写业务代码还长，而且测试永远只能覆盖我想到的情况。

所以当我看到 erkamyaman/rust-anything 这个项目时，我的感觉是：它把我那三个月手搓的活儿，做成了一个工具。

2026 年 11 月 16 日它发布了 1.0.0，三天后就到了 3321 个 star。仓库在 erkamyaman/rust-anything，MIT 许可证，主语言 Rust。

它的一句话定位是：

Rewrite your whole app in Rust, one piece at a time, checked against the original at every step.

翻译过来就是：把整个应用一块一块改写成 Rust，每一步都跟原版对照检查。

下面我们拆开看它到底怎么做到的。

二、它是什么：一句话加上几个关键数字

rust-anything 不是代码翻译器。它不生成 Rust 代码。

它提供的是一套” 工作流 + 脚手架 + 验证机制”，Rust 代码由你或者你的 coding agent 写在一份叫 port.rs 的文件里。它负责的是 agent 干不好的那部分：

  • 哪段代码值得迁移（profile）
  • 按什么顺序迁移（analyze）
  • 怎么让 Rust 代码能被原来的调用方调用（bridge）
  • 原来的行为到底是什么（record）
  • Rust 写得对不对（diff）
  • 迁移完到底快不快（bench）
  • 上线时怎么保证不出事（shadow、gate）
  • 怎么从” 一半 Rust 一半 Node” 变成” 纯 Rust”（app record 到 app lift）

三、核心机制一：先测，后改

rust-anything 的整个设计，源自一个想法：别让 AI 去猜” 原来那个函数的行为是什么”，让它去录。

这就是 record（rust-anything record rust/fuzzy-rs），这条命令做三件事。

一、生成边界用例。 从函数签名推断参数类型，然后生成一堆” 语义陷阱”：非 ASCII 字符、emoji、-0、NaN、Infinity、本该是浮点却传了整数、字符串长度和大小写边界、有符号除法、溢出边界、浮点打印格式、Map 和 Set 的遍历顺序。README 里提到的具体陷阱包括土耳其语的点 less i（ı）、Kelvin 符号（K）、长 s（ſ）、阿拉伯 - 印度数字、行分隔符、final sigma。

二、跑你自己的输入。 --inputs cases.jsonl 可以喂自己的 JSONL 文件。

三、跑原版自己的测试。 这个是杀手锏：

它在测试跑的时候” 偷看” 原函数的每一次调用，把调用参数和返回值都录下来。官方案例 vercel/ms 从它自己的 167 个 Jest 测试里抓到了 340 次真实调用。作者在文档里说，第一次移植时是手工从测试里抄了 149 个输入，后来才有了 --from-tests。

录下来的东西存成 cases.jsonl，每个用例是一次函数调用加上它的返回值或者抛出的异常。然后 diff 把这些用例全部回放给 Rust 版（rust-anything diff rust/fuzzy-rs），有任何一条对不上它就列出来。

两个容易被忽略的细节

第一，两边都抛异常算” 一致”。 DECISIONS.md 里记着：

L7 | Both sides throwing counts as agreement; messages are not compared.

原版抛 TypeError，Rust 版抛 ValueError—— 只要两边都是” 抛了” 就算一致，错误消息文本不算契约。理由很实在：错误文本很少是真正的契约，如果要比，很多移植会卡在措辞上而不是逻辑上。Go 是例外，它的 error 值按消息比较，因为 Go 的调用方经常直接比错误字符串。

第二，录的时候跑两遍。 record 把每个用例跑两遍，比对差异：值变了（时间戳、随机 ID）→ 变成 [..] 通配符；同样的行但顺序不同（哈希表遍历、并发）→ 按任意顺序比较；行数不同 → 变成 ...，匹配任何东西。这些都会列在 noise 报告里要求你逐条看。文档说得很直白：”look at every one, since a hash-order or concurrency difference is exactly what can change for real in a port.”（app record 这一层同样跑两遍。）

四、核心机制二：挡住” 原来那版变了”

如果原版代码后来被改了，之前录的行为还有效吗？

rust-anything 的做法是：record 保存被录单元文件的指纹，写进 recorded-from.json。以后原版变了，diff 会警告，gate 直接失败，直到你重新录一遍。

An original that moved on. record saves a fingerprint of the unit’s files (recorded-from.json); when the original changes later, diff warns and gate fails until you record again, instead of passing against what the original used to do.

这条我觉得是整套东西里最被低估的设计。因为真实项目里最常见的事故不是” 移植写错了”，而是” 移植写对了，但原版早就变了，测试用例还是三个月前的”。有了指纹，这个问题至少不会静默通过。

五、核心机制三：bridge 生成桥接，但把 Rust 代码留给你

bridge 做的是生成脚手架：

生成的东西是一个 crate：Cargo.toml、src/lib.rs（napi-rs 或 wasm-bindgen 绑定）、src/port.rs（你或你的 agent 在这里写 Rust，初始是空桩）、src/js.rs（JS 语义的忠实模拟辅助函数），以及 rust-anything.json。

DECISIONS.md 里解释了这个拆分：

L1 | bridge splits lib.rs (bindings) from port.rs (plain Rust, #![forbid(unsafe_code)]). | Binding macros expand to unsafe code; the port itself never needs it, and it stays testable without a JS runtime.

翻译一下：绑定宏会展开成 unsafe 代码，但你的移植逻辑本身不需要 unsafe。而且这样 port.rs 不用挂着一个 JS 运行时也能测。

各语言用什么桥

语言 桥接方式
TypeScript/JavaScript napi-rs 或 wasm-bindgen，生成二进制 wire 格式；类和 async 都支持
Python PyO3（abi3），直接类型转换，带类型的异常
C extern "C" 函数，保留原函数名 + 头文件
Go 类型化的 cgo 调用 + 生成的二进制 wire，放在一个保留原 API 的包里
Ruby magnus 扩展，放在原模块下
Java 类型化 JNI + 生成的二进制 wire，放在保留原方法的包装类里
PHP（preview） 待做：PHP FFI over C ABI
C#（preview） 待做：P/Invoke over C ABI

Rust 那边的 src/lang/ 目录，每个语言一个文件，最大的是 src/lang/python.rs（45 KB）和 src/lang/php.rs（34 KB）。

哪些东西不能跨桥

这是最实用的一段。bridge 会自动把” 跨不过去” 的导出留在原语言里，并说明理由。TypeScript 的话：接收或返回函数的、生成器和迭代器、RegExp、instanceof 检查、泛型（可以用 --as-json T 桥接一个只填数据的类型参数）、以及类型里（跟着 import、re-export、extends 一路追下去）藏了函数的。

作者在 x18n 项目上发现：55 个导出里有 26 个属于这一类。这些如果硬移植，会改掉公开 API 或者悄悄坏掉。剩下的放进 Rust 的 API 和原来完全一样，调用方一行都不用改。

JSON 表达不了的东西怎么办

这是我写 Rust 迁移时踩过最多次的坑。JSON 表达不了 undefined、NaN、Infinity、-0、孤立代理对（lone surrogate）。rust-anything 的做法是给结构化值带标记（{"$undefined": true}、{"$num": "NaN"}、{"$utf16": [...]}），生成的 index.cjs 负责翻译。

X2 这条决策记录了这些标记每一个的真实来源：

Each one produced real mismatches: splitKey‘s namespace: undefined, toWireRange with NaN, diffText splitting an emoji, isOutdated(change) with one argument.

每一个标记背后都是一个真实的 bug。孤立代理对那个，是被 fixture 测试发现的 ——JS 的 slice 能把一个 emoji 切成两半。

六、核心机制四：--batch 才是真正快的地方

这是我读完全部文档后觉得最有价值、也最反直觉的一节。

README 里有一句警告：

Calling Rust once per small function is usually slower than a JIT; rust-anything finds the loop worth moving, and moves it.

翻译：小函数每次调用都跨一次桥，通常比 JIT 还慢。rust-anything 帮你找到那个值得搬的循环，然后把整个循环搬走。

为什么会慢

因为跨桥有成本。DECISIONS.md 里的实测：

S1 | … JSON cost 10-50x the work: the colorsys port took 11.7 µs per call, CPython 0.5 µs.

Python 的 colorsys 移植一次调用 11.7 微秒，CPython 原生 0.5 微秒，差 23 倍 —— 跨桥的开销比业务逻辑本身还大一个数量级。所以关键不是” 把函数写快”，而是” 别每次都跨”。

实测数字

demo/ 目录里每个都有可复现的 benchmark。x18n 的侧边栏搜索，5 万个 key，4 核：

看清楚第 3 行：同一个移植，逐个调用反而比原版慢。这就是为什么 profile 必须先跑。

FuzzyScoreIndex 是什么

这是 port.rs 里的一个 struct，作者手写的，设计很讲究：每个 key 预先转小写并附带字符掩码；建一张表记录每个常见字符在每个 key 里第一次出现的位置（一个字母的查询就是一列）；缓存上一次查询的匹配结果，接着输 se 的时候只重算 s 匹配过的那部分。

DECISIONS.md 里有一句：

S15 | An index in port.rs may define its own rank(<fixed>, min); the generated rank of every language then calls it instead of ranking run‘s results.

排序可以比全部打分便宜：x18n 的 index 收窄到上次查询的匹配项，单字母查询直接查表，wasm 上从 1.7x 提到 11.5x。而 S10 说明了为什么这个设计能成立：

Preparing items once (lowercasing, masks) was the second 4x on x18n search; one port.rs then builds for napi and wasm.

也就是一份 port.rs，同时编译成 napi 版本和 wasm 版本。桥接方式可以换，算法代码不用动。

Go 和 Java 只快 3-4 倍，因为它们原本就是编译型语言，逐项调用本来就已经很快，批量的收益主要来自多核。文档里那句总结很实在：

Compiled originals gain less: the per-item work is already fast, so the batch wins by the number of cores.

一个小坑：mimalloc

DECISIONS.md 的 S12 记着，带批量的 crate 用 mimalloc 作全局分配器：系统分配器会把线程串行化（纯 Rust 4 核只有 1.6x，在 Go 进程里甚至比单线程还慢），换 mimalloc 后是 3.2x。

七、核心机制五：profile —— 迁移顺序也是数据决定的

移植顺序不是拍脑袋定的。

它用目标语言自己的 profiler 跑一个真实负载：Node.js 用 node --cpu-prof，Python 用 cProfile，Go 用 go test -cpuprofile 加 go tool pprof -raw（保留内联帧），Java 用 JFR 执行采样，Ruby 用通过 RUBYOPT 加载的 TracePoint 调用追踪器。

Ruby 那条在 DECISIONS.md 里有解释：

Ruby has none built in that samples, and stackprof is a gem the repository may not have.

所以用 TracePoint 自己写了一个。文档也承认代价：”The Ruby tracer slows the program several times; shares stay comparable.”

输出的不只是” 哪些函数热”，还有谁在调用它、哪些循环值得批量。S8 这条决策说得最清楚：

Which code to port is a property of how it is called, not of the code: x18n’s fuzzyScore is a leaf (slower in Rust per call) but a quarter of a search, called 50,000 times by one loop.

fuzzyScore 单独看是个叶子函数，移植过去一定更慢。但它是整个搜索的四分之一时间，被一个循环调用了 5 万次。

只看代码你永远看不出来这件事，只有 profile 能看出来。

analyze 排顺序

rust-anything analyze . 输出：单元划分、迁移顺序（wave）、风险带 file:line、每个单元用什么桥、依赖到 crate 的映射，以及 start_here（最值得先动的几个）。

单元的 wave 来自单元图的强连通分量：

A5 | Waves come from strongly connected components of the unit graph. | Leaves first means a Rust unit never calls back into JS; cycles must move together.

叶子先动，意味着 Rust 单元永远不会回调 JS；有循环依赖的必须一起搬。

A6 这条决策解释了为什么用启发式：

False positives cost a look; false negatives cost silent bugs.

误报只是多看一眼，漏报是静默的 bug。所以宁可多报。

就绪度与优先级的公式

A7 规定就绪度 = 100 − 加权风险（取对数）− 规模 − fan-in − 依赖惩罚 + 测试加分。A8 规定优先级 = 一半就绪度 + 一半价值（每行的循环和字符串工作量、有没有测试、规模是否在 80 到 600 行之间）。

就绪度算的是” 安不安全”，优先级是” 安不安全 + 值不值得”，对半分。为什么对半？A8 的理由：

Readiness alone picks trivial declaration files.

只按就绪度排，你会先挑到一堆只有类型声明的空文件。

八、核心机制六：shadow 和 gate —— 上线前的两道闸

shadow：新旧并行跑

生成一个 drop-in 替换模块，它同时跑原版和 Rust 版，返回原版的结果，同时把不一致的地方报出来。

L9 这条决策说得很清楚：

Shadow mode returns the original’s result, runs Rust second, and never lets Rust errors reach callers. | Shipping shadow code must not change behavior; only the report sees Rust.

为什么要这个模式？D5 引了 Cloudflare FL2 的做法：

Cloudflare FL2 ran old and new side by side in one process and moved traffic gradually. Tests prove a port; production traffic confirms it.

测试证明移植是对的，生产流量才能最终确认。 而且这个需求不是 Rust 独有的，所以每种语言都有 shadow 模式 ——Ruby 用 prepend，Java 用 <Class>Shadow 类，C 用 -D 重命名加一个 shadow crate feature，Go 就是一个包。

gate：一整套” 做完了” 的定义

gate 一次性检查：

  • cargo fmt
  • cargo clippy -- -D warnings
  • cargo test
  • unsafe 审计：只允许有 // SAFETY: 注释的
  • 没有未实现的函数
  • 构建通过
  • API 存在
  • 行为一致（录的用例全部匹配）
  • 错误路径全覆盖：原版的每条错误路径都要有一个录下来的失败用例
  • 原始版没报错的地方，Rust 不能 unwrap/expect/panic!（除非标了 // INFALLIBLE: <why>）
  • 代码规模：Rust 版行数不能超过原版的 3 倍（外加 50 行给 import 和签名）

规模这条在 FAQ 里有解释：

gate compares the port’s lines with the original’s and fails above 3x (plus 50 lines for imports and signatures): that usually means hand-writing what a crate already does, or handling cases one by one. | analyze lists the crates to use.

意思就是：如果你 Rust 写了三倍多的行数，通常说明你在手写一个现成的 crate 该干的事。

bench 单独存在，不并进 gate

X5：

bench is a separate step, not part of gate. | Speed is not correctness, but it decides whether a port should ship: every x18n core port was correct and slower.

x18n core 的每一个移植都是正确的，但是更慢的。如果 bench 在 gate 里，这些移植根本过不了门。

S4 记录了 bench 的结论逻辑：

bench ends with a verdict: ship, keep the slower functions, port a bigger unit, or (for C) optimize the port. Faster is 1.1x or more, slower under 0.9x.

四个结论：可以上线 / 保留原版（更慢的那些函数） / 换一个更大的单元来移植 / （C 的话）优化这个移植。

注意阈值是不对称的：1.1 倍算快，0.9 倍以下算慢。中间地带算” 持平”。

九、核心机制七：整个应用的迁移 —— app 系列

前面都是单个函数或模块。但真实需求是” 把整个应用变成 Rust”。

这是 v1.1.0 引入的，也是我认为这个项目最有野心的部分。

五个命令

app record：黑盒录整个应用

应用是黑盒。app record 会跑三组用例：应用文档里的例子（README 和 shell 文件里的 $ mytool ... 行，还有那些例子提到的文件）、--inputs 提供的 JSONL（{"name", "args", "stdin", "env", "files"}）、以及语义陷阱（非 ASCII 和 emoji 字符串、负除数和负取模、溢出、极大和极小的浮点、map 顺序、文件不存在）。每个用例跑两遍，差异变成通配符。

用例存成 trycmd 格式的文件（hello.toml 存 argv/env/exit code，.stdin、.stdout、.stderr、.in/ 输入文件、.out/ 写出的文件），可以直接手工编辑，Rust 侧有现成的测试跑它们。

app replay：一个数字加一份报告

rust-anything app replay . 输出 passed/total，写一份 rust/app-cases/replay-report.md，每个失败的用例带 diff，任何不匹配就非零退出。

报告里没有时间戳，也没有临时路径 —— 同一个 build 跑两次 replay，写出来的文件一模一样。这是为了能进 CI：

Commit it and run app replay then git diff --exit-code rust/app-cases/replay-report.md in CI, and a half-ported app fails CI on any change in what passes, better or worse, until the report is updated with it.

半迁移状态的应用，只要通过率有变化（不管是变好还是变坏）CI 就会红，直到有人更新报告。这个设计把” 迁移进度” 变成了一个可版本控制的、CI 可校验的东西。

app front-door：Rust 前门

rust-anything app front-door . 生成 rust/app，一个以应用命名的 Rust 二进制：clap 解析器负责命令和参数，每个命令转发给原版，原版输出和退出码原样透传，每次 fallback 都计数。所以一上来 replay 是 100% 通过、100% fallback—— 它构建并回放来证明这一点。

它从不覆盖 rust/app：一旦生成，代码就是你的了。

app wire：一块一块把命令交给 Rust

rust-anything app wire . textkit --command upper 会在单元 crate 上跑 gate、把它作为库加进 rust/app、写一个胶水桩（src/units/textkit.rs）、重新生成路由，然后构建并回放。胶水桩留给你写：

writes a glue stub (src/units/.rs, yours to write: parse args, call ::port, print what the original prints)

还有一个 kill switch：RUST_ANYTHING_UNIT_TEXTKIT=original 设了这个环境变量，wired 单元就退回原版。这是生产环境出问题时最快的回滚方式。

app lift：变成纯 Rust

rust-anything app lift . 会先检查并拒绝，列出所有阻塞项：还有用例在 fallback、胶水还是桩、有单元没过 gate。

都过了之后，它先在副本上操作：移除 fallback 路径和 kill switch，把每个单元 crate 变成 rust/app 的普通库（不再有 cdylib、绑定和生成的包装），加上 rust/app/tests/app_cases.rs，让 cargo test 就能跑 app-cases。

然后跑一遍 lift 清单：fmt、clippy、测试、rust/DECISIONS.md 里提到的每个 target、运行时读取的文件和没被嵌入的资源、纯二进制上的 replay。

全部通过之后才写回。原版永远不动。

HTTP 服务器

同一套命令证明 HTTP 服务器：

--http 表示命令会启动一个服务器，端口从 PORT 环境变量或命令里的 {port} 取。请求来源是应用文档里的 curl 行、--inputs（{"name", "method", "path", "headers", "body"}）和陷阱 —— 路径段与查询值换成跟 CLI 参数一样的陷阱，body 用文本和 JSON 陷阱，再加一个未知路由。

每次运行都重新启动服务器，按名字顺序发请求，所以请求之间的状态是保留的。还有两个服务器专属选项：--fresh db.json（服务器读写状态文件时，每次启动都从快照复制一份到新的工作目录）和 --pace 50（每个响应后等 50 毫秒）。

--pace 是被 json-server 的真实 bug 逼出来的：

Found in json-server: after each of its own writes, its file watcher reloads the file. When the next request writes before that reload ends, the reload can wipe that write out: the first recording, sent as fast as the server answered, had a POST answered 201 that later reads did not show.

json-server 每次写完文件，文件监视器会重新加载文件。如果下一个请求在重载完成前就写，重载会把那次写覆盖掉。第一次录制时（请求发得跟服务器回的一样快），有个 POST 返回了 201，但后来读的时候看不到那条数据。所以录制时必须加 --pace 50。

前门是 axum 服务器，在另一个端口上启动原版，把没有单元应答的路由全部代理过去。

十一、它是怎么做 Agent 集成的

这是我觉得设计上最聪明的一块。

D1 这条决策是整个项目的定调：

A toolkit your agent drives, not a translator that calls a model itself. | No model cost or vendor lock-in; works with any agent. | The checks are the part an agent cannot do reliably.

翻译：这是个你的 Agent 驱动的工具箱，不是个自己调用模型的翻译器。没有模型成本，没有厂商锁定，跟任何 Agent 都能配合。检查这件事，Agent 自己做不可靠。

所以它同时提供两种形态：

CLI（人可以自己跑）和 MCP server（Agent 调工具）。

rust-anything setup 一条命令，把 MCP server 和工作流 skill 都注册到你找到的每个 Agent 里：Claude Code 写 ~/.claude.json 和 ~/.claude/skills/，Codex 写 ~/.codex/config.toml 和 ~/.codex/skills/，Cursor 写 ~/.cursor/mcp.json，Gemini CLI 写 ~/.gemini/settings.json；其他 MCP 客户端可以手动加 rust-anything mcp 作为 stdio server。

S16 这条决策专门讲了怎么不弄坏你的配置：

setup writes each agent’s own config … adding only the rust-anything entries, keeping key order, writing through a temporary file, and refusing files that do not parse. | A tool that rewrites someone’s settings must never lose them.

只加 rust-anything 相关的条目，保留 key 顺序，通过临时文件写入，遇到解析不了的文件直接拒绝。 改别人配置的工具绝不能把别人配置搞丢。改文件之前还会备份（<file>.rust-anything.bak），--remove 可以撤销。

MCP 工具就是 CLI 命令的一一对应（docs/tools.md 明确说了 “Every tool is also a CLI command with the same options”），所以 Agent 可以调 analyze、bridge、record、diff、bench、shadow、gate、app_record、app_replay、app_front_door、app_wire、app_lift 这些。

README 里给了几个问法：” 用 rust-anything 把这个 CLI 端到端重写成 Rust，并证明行为一致。”” 这个搜索感觉很慢，用 rust-anything profile 一下，把热循环搬到 Rust。”” 在 rust/text-rs 上 bench 一下 Rust 移植版，告诉我该不该上线。”

十二、它做对的几个设计决定

我想单独拎出几条 DECISIONS.md 里我认为最有价值的。

1. 保守优先

A6 | False positives cost a look; false negatives cost silent bugs.

误报只是多看一眼，漏报是静默的 bug。整个工具的设计基调是” 宁可吵，不可漏”。

2. 不猜

A9 | The library-to-crate table (src/crates.toml, every language) is hand-curated; unknown packages are reported as unknown, never guessed. | The prompt: flag missing equivalents instead of hand-rolling silently.

crate 映射表是手工维护的（src/crates.toml，19 KB）。找不到对应 crate 的包，一律报 unknown，绝不猜。 如果它猜错了，你会得到一个能编译但行为完全不同的实现 —— 而这正是这个项目要消灭的东西。

3. JSON 输出带版本

A10 | JSON output carries schema: rust-anything/analyze@1. | Agents read it; it is a wire contract and gets versioned.

因为 Agent 要读这个 JSON，所以它是一份 wire contract，得有版本号。

4. 只在端点检查行为，不检查内部

The recordings check behavior at the app’s edges (a CLI’s output, a server’s responses, a module’s exported functions), not its internals. | Mirror the old structure while units still cross the bridge; once app lift has removed the original, restructure the Rust freely, and app replay still proves the behavior.

意思是：录制只检查边界行为（CLI 输出、服务器响应、模块导出），不检查内部实现。过渡期你可以照着老结构写，等 lift 做完把原版拿掉了，Rust 内部就可以随便重构，app replay 依然能证明行为。这解决了我一开始担心的那个问题 ——“会不会被老代码的设计锁死”。

5. 方向是单向的

Nothing calls back into the original either: the front door runs it as a separate process (or forwards HTTP to it), bridged units are called by the original and never the other way round, and callbacks stay in the source language.

原版永远不会被 Rust 回调。前门把它当独立进程跑（或者把 HTTP 转发过去），被桥接的单元是原版调 Rust，反过来不行。这保证了不会有” 互相调用” 导致的死锁或无限递归。

6. 你的代码不出本机

Does my code leave my machine? No: rust-anything runs locally and sends none of your code anywhere. | Cargo downloads crates as usual, and your agent’s model provider sees what your agent sends it, under its own policy.

十三、诚实的局限

这一节我尽量写全，因为对判断” 该不该用” 最重要。

录不到的就查不出来

文档里有一节叫 “What it can’t catch”，写得非常诚实。

没录过的输入。 生成的用例、语义陷阱、原版的测试套件（record --from-tests）和你自己的 --inputs，就是天花板。而文档说得很直接：

Add real inputs (production samples, bug reports); the user input that breaks prod is rarely one a generator thinks of.

会破坏生产的那个用户输入，生成器基本想不到。 这一条我认为是最要命的。

正则。 Rust 的 regex crate 没有 lookaround 和反向引用，而且就算能编译的 pattern，\w、\b、\d 和非 ASCII 上的大小写不敏感匹配，在 JS、Python、Java 之间都不一样。换 fancy-regex 或重写 pattern，可能通过所有录制的用例，但在土耳其语的点 less i 或者零宽连接符上还是不一样。record 会给每个用到正则的文件的每个函数加正则陷阱，但文档还是建议你拿真实 pattern 对真实文本 fuzz 一遍。

运行时会变的东西。 时间、内存、负载下的并发行为、以及 stdout/stderr/ 退出码 / 写出的文件 / HTTP 响应之外的副作用（网络调用、数据库、信号）都不比较。

浮点数。 数字转文本的格式在不同语言里不一样（1e21、-0、位数）。--float-tolerance 只宽容舍入，永远不宽容格式。

其他平台。 录制只能证明录制那台机器上的行为。依赖类型大小、字节序或编译器的 C 代码在目标平台上可能完全不同 —— 所以 analyze 会把面向硬件的 C 留在 C 里。

profile 只是”Tested” 状态

STATUS.md 里，命令的状态是分级的：Verified（端到端跑过真实代码）、Tested（有 fixture 测试但没跑过真实项目）、Preview。

而 profile 是 Tested，不是 Verified：

命令 状态
analyze Verified（x18n 的 142 个单元）
bridge、record、diff、gate、build Verified
bench Verified
record --from-tests Verified (TS/JS)，Tested (Python)
--batch Verified
wasm bridge Verified
shadow Verified
profile Tested
app record、app replay Verified (servers)，Tested (CLIs)
front-door、wire Verified (TS server)
lift Verified (TS server)，Tested (CLIs)
MCP server Tested

所以这个工作流里，最前端的那一环（profile）反而是最没被真实项目检验过的。这是个有点尴尬的事实，值得知道。

各语言的支持程度差别很大

从 DECISIONS.md 的 “Known limits”：

  • C：只有标量和 const char * 的 API 能跨桥。输出缓冲区（char *out, size_t *len）和状态结构留在 C，通过宏定义的函数看不到。
  • Go：方法、泛型、可变参数、指针、接口和 channel 留在 Go。结构体参数以 JSON 跨（用导出字段）。
  • Ruby：只支持模块函数（def self.x、module_function）。类和接受 block 的方法留在 Ruby。
  • Java：只支持 public 类的 public static 方法。重载、泛型、char 和对象类型留在 Java。而且 record 只用 javac 单独编译模块源码，所以依赖 Maven classpath 的代码现在还录不了。
  • Shadow 模式只比对同步结果：会改参数的函数，第二个实现拿到的是已经被改过的输入。

C 还有一条特殊情况：

M5 | C records each case in a forked child; a crash is recorded as crash: <signal> and accepts any port behavior. | Inputs outside a C function’s contract are undefined behavior: real glibc segfaults on isalpha(INT_MAX).

C 的每个用例都在 fork 出的子进程里跑，崩溃记成 crash: <signal> 并接受任何移植行为。因为超出 C 函数契约的输入就是未定义行为 —— 真实的 glibc 在 isalpha(INT_MAX) 上就会 segfault。

浮点数基本匹配不了

FAQ 里说得很直接：

Often not: operation order, fused multiply-add and the math library differ between compilers.

如果你的代码是数值计算，--float-tolerance 1e-9 能宽容舍入，但整数、文本和结构必须完全一致。

它不翻译代码，也不认识二进制

It ports source code: it parses the functions, records what each one does, and checks the Rust against the running original. | A compiled app has none of that to work with, and analyze says so.

APK、JAR、exe 这种编译产物是搞不定的。” 根据二进制的可见行为重写一个 Rust 应用” 是另一个项目。

Kodebase 结构上的限制

  • Fuse.js 那种” 整个 src/ 在一个 import 环里” 的项目，不能按文件逐个移植。作者得绕路走适配器。
  • Go 的 profile 必须来自 go test 跑，因为 Go 的 pprof 只能在进程内用。
  • Ruby 的追踪器会让程序慢好几倍。
  • Ruby 用 alias 建的别名会复制原方法，所以 shadow 模式看不到通过别名的调用。

项目非常新

仓库 2026 年 11 月 16 日创建，今天是 19 日。三天。

v1.0.0 到 v1.5.1 一共 9 个 release，全在 11 月 16 日到 18 日之间。这三天里作者自己也在疯狂修 bug（v1.5.1 修的就是 recorder 卡死的问题 —— 某个生成的输入让原版跑飞了，比如 [w] * n 分配几个 GB）。

虽然作者很勤快（156 次提交，第二名贡献者 46 次），但任何 3 天大的项目都不该直接用在生产环境。

十四、跟同类项目比

vs. 用 AI 直接重写

这是最直接的对比，也是最有价值的对比。

AI 直接重写的流程是：给上下文 → 生成代码 → 跑测试 → 修。问题在于：AI 猜语义（UTF-16 vs UTF-8、Math.round 的方向、-0 的打印、正则语义 —— 这些 AI 经常知道，但不知道的更多）；没有基线（AI 写完你怎么知道它对？你得自己写测试，那比重写还累）；“跑通测试” 不等于” 行为一致”（你现有的测试只覆盖你写过的路径）。

rust-anything 的价值在于：它把” 行为一致” 这个模糊目标变成了一个机械的、可重复的、可进 CI 的检查。AI 依然要写 Rust，但写的是算法，而不是语义 —— 语义由录制固定。

DECISIONS.md 那句话说得最好：

The checks are the part an agent cannot do reliably.

vs. C2Rust / TRACTOR / Depyler

C2Rust 是最著名的 C 到 Rust 翻译器，但它只能处理 C（rust-anything 支持 6 种语言），而且是翻译（transpile），产出” 能编译的等价物”，不保证行为一致，也没有录制 / 回放机制。

DARPA 的 TRACTOR 项目（2025 年）是 C 到 Rust 的转换研究项目，目标是全程序转换加形式化验证。rust-anything 的路子不一样：它不追求全程序转换，追求增量、可验证、可回滚。TRACTOR 那套更适合一次性转换，而真实项目里几乎没人能接受” 整个仓库冻结几个月”。

Depyler 尝试用 AI 把 Python 转成 Rust，有意思的实验，但产出质量不稳定。

rust-anything 选了 TS/JS 作为第一语言（D2），理由是：

No existing tool covers TS/JS to Rust. C/C++ and Python are crowded (DARPA TRACTOR, C2rust, Depyler).

它的立场正好相反：不让 AI 写转换逻辑，只让 AI 写算法。

vs. wasm-pack / PyO3 等桥接库

这些是底层工具，rust-anything 是上层工作流。

wasm-pack 帮你把 Rust 编译成浏览器能用的 wasm，但它不告诉你该编译什么、不保证行为一致、也不管迁移顺序。

rust-anything 在这些之上加了：选谁、什么顺序、怎么验、什么时候能上线。

vs. 手工做 differential testing

最像的对比对象。手写 fixture、手写对照测试，跟 rust-anything 的 record/diff 思路一致。

差别在于覆盖面和自动化程度。rust-anything 的优势是自动生成边界值和语义陷阱，而且陷阱清单是踩过坑积累出来的（UTF-16、孤立代理对、-0、final sigma……）。人写测试很难想到孤立代理对这种。

劣势是：它只能发现你想到的陷阱。你自己的领域知识（比如” 这个函数在负数上语义特殊”）还是得靠你自己喂 --inputs。

它填补的位置是：AI 编码工具和语言迁移工具之间的那一层。

十五、适合谁，不适合谁

适合

1. 你的项目有明确的性能瓶颈，而且瓶颈是” 热循环”。 最理想的场景，整套 --batch 机制就是为它设计的，profile 会告诉你哪里是。

2. 你在做增量迁移，不想冻结整个仓库。 app front-door → app wire → app lift 这条路就是为增量设计的，每一块都可以单独上线、单独回滚（RUST_ANYTHING_UNIT_<NAME>=original）。

3. 你想用 AI 写 Rust，但担心它会悄悄改变行为。 这正是 D1 那条决策的定位。

4. 你的代码库有测试套件。 record --from-tests 能从测试里抓到真实调用，录制质量会高很多，vercel/ms 的例子就是这么做的。

5. 你在做 CLI 或 HTTP 服务。 app 系列对 CLI 和服务器有一等公民支持，json-server 那套流程可以直接抄。

6. 你想给开源项目做性能 PR。 Fuse.js 那个案例就是模板：写一个适配器，录 3000 多个用例，diff 全过，然后提 PR。

不适合

1. 你的项目本身就是 Python/Go/Java，而且没到性能瓶颈。 从 vercel/ms 的结论看：0.56x，慢了快一倍。

2. 你的代码大量依赖正则、反射、动态特性。 analyze 会把这些标成 high 风险，你要么留在原语言，要么接受大量手工工作。

3. 数值计算代码。 浮点匹配基本做不到，容差机制只是缓解。

4. 你想要一个” 一键全量翻译” 的东西。 它明确不是这个。D2 说得很清楚：TS/JS 优先，因为 C/C++ 和 Python 那块已经挤满了。

5. 你的项目没有行为可录。 比如根本没有可运行的原版，或者原版已经跑不起来。没有基线，一切免谈。

6. 你在生产环境里，需要今天就用。 三天大的项目，三天里发了 9 个 release。作者显然在高强度迭代，但这意味着 API 还会变，文档可能跟实现不同步。

7. 你想要的是”AI 帮我把代码全翻译一遍”。 它是工作流，不是翻译器，而且这个定位是有意的。

十六、我的实际使用建议

如果你要用，我建议这个顺序：

第一步，先跑 analyze 看看它怎么说。 rust-anything analyze . 是只读的，零风险，它会告诉你单元划分、风险点、start_here（最值得先动的）。如果它的 start_here 让你认同，再往下走；不认同就别勉强。

第二步，选一个小单元试水。 不要一上来就 app record --whole-app。先挑一个 analyze 推荐的小单元走完 bridge → record → diff → gate，体会一下录制的质量 —— 看 cases.jsonl 里生成的用例有没有覆盖你真正在意的那些边界，覆盖得不好就先用 --inputs 喂自己的真实输入。

第三步，跑 profile。 注意这是我前面提到的唯一一个 “Tested” 而不是 “Verified” 的命令。你可以拿它当参考，别完全信。

第四步，才是 app record。 这一步最耗时（json-server 录了 514 个 HTTP 用例），而且会真的运行你的原版。README 里有很严肃的警告：

record and app record run your original code, calling each function (or the whole app) on many generated inputs, and app record runs every case twice. | Code that writes files, talks to a database or calls the network does that once per case. | Run them on a copy of the project, with a test database and no production credentials in the environment.

写文件的、连数据库的、调网络的代码，每个用例都会真的执行一次。 在副本上跑，用测试数据库，环境变量里别放生产凭证。

这句话我要再强调一遍，因为这是最容易出事的地方。我的第一反应肯定是” 在仓库目录里直接录一下”，但如果那个仓库连着生产库……

第五步，lift 之前把所有 app record 的用例跑通。

lift 会拒绝并列出阻塞项，这是好事。但你要确保 514 个用例全绿，而不是”99.8% 通过”（json-server 的 front-door 阶段就是 513/514）。

十七、最后

回到我开头那个丢人的场景：Claude Code 一小时给我 900 行 Rust，138 个用例挂了 71 个。

如果当时有 rust-anything，流程会是：

  1. analyze 告诉我 src/parser/ 有 14 个单元，3 个有 high 风险
  2. bridge 生成 crate 和空桩
  3. record 录下 200 个边界用例，其中包括 UTF-16 偏移、-0、正则陷阱
  4. Claude Code 在 port.rs 里写实现
  5. diff 告诉我哪几条对不上，并且是具体哪条输入
  6. Claude Code 修，直到 200/200
  7. gate 确认 fmt、clippy、测试、错误路径、代码规模
  8. bench 说” 可以上线” 或者” 别动它”
  9. shadow 在生产灰度，新旧并行
  10. 下一个单元

同一件事，可能从两周变成一天。

我想强调的不是它有多强，而是它选了一个正确的战场。

“用 AI 重写代码” 这个叙事里，AI 写代码已经够好了，好到瓶颈不在那里。瓶颈在验证。而验证是机械的、可重复的、适合用程序做的。

rust-anything 的作者显然想明白了这件事 ——D1 那句 “The checks are the part an agent cannot do reliably” 是整个项目的题眼。

它不聪明，也不试图聪明。它只是把” 证明这两个实现行为一致” 这件苦活，做成了一条命令。
