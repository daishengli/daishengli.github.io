EL4CTEO/fast-anything：1869 star 的工具，让 AI Agent 只把最慢的 5% 改写成 Rust 并证明行为一致

发表于 2026-11-23 分类于 开源项目
fast-anything 是 2026 年 11 月 21 日上线的新项目，两天拿到 1869 个 star，MIT 许可证，主语言 Rust。它不做整应用重写，而是先用各语言自带的 profiler 把一次真实运行里的函数按耗时与可移植性排序，筛出既慢又干净的热点，再让 Claude Code 或 Codex 等编码 Agent 只把这些函数改写成 Rust，最后用录制的真实调用逐条回放比对：只有返回值一致、异常类型一致、单次调用不比原实现慢，才允许启用。工具支持 Python、JavaScript 与 TypeScript、Ruby、Java、Go、PHP、C、C++、C# 等十种语言，绑定分别用 PyO3、napi-rs 和统一的 C ABI 加 JSON 桥接。verify 除了回放最多 500 条真实调用，还会派生 NaN、负零、非 ASCII 文本等边界用例，并让原实现回答收缩输入，一致率不到 100% 一律不许上线。

EL4CTEO/fast-anything：1869 star 的工具，让 AI Agent 只把最慢的 5% 改写成 Rust 并证明行为一致

一、一个让我沉默了三秒的需求

上周开会，有人提了个需求，原话我记到现在：

“我们那个 Python 报表服务太慢了，能不能用 Rust 重写一下？”

我当场就想说” 好”，然后停住了。

因为过去两年我听过这句话太多次了。每次的结果都一样 —— 重写三个月，中间发现一个新的业务规则没覆盖，测试用例没人补，最后旧版本继续跑，新版本躺在仓库里吃灰。旧项目不是不能重写，是重写的成本从来不是写代码，而是证明写出来的东西跟原来一样。

更扎心的是性能数据本身就不支持重写。一个典型的报表服务，真正耗时的可能就是那两个字符串相似度比较函数，占了总耗时的 80%。剩下 80% 的代码 —— 配置解析、数据库查询、模板渲染、异常处理 —— 一共占 20%，重写它们收益为零，风险却包圆了。

所以现在我听到” 重写成 Rust” 这个需求，第一反应变成了三个问题：

  1. 到底哪几个函数慢？
  2. 这几个函数能不能干净地挪到 Rust？
  3. 挪过去之后，凭什么说它跟原来一样？

第三个问题最难回答。人工做这件事非常痛苦，因为你要构造几十组输入、覆盖各种边界、逐个比对。这活儿枯燥、重复、极易漏，而且漏了就是线上事故。

11 月 21 日，一个叫 EL4CTEO/fast-anything 的仓库在 GitHub 上出现了。两天时间，1869 个 star，109 个 fork。它的 README 第一行写着：

Don’t rewrite it in Rust. Rewrite the 5% that’s slow.

（别把它整个重写成 Rust。只重写那慢的 5%。）

这句话基本上把这个项目的全部主张都说完了。

二、它到底是什么

一句话定义：fast-anything 是一个” 局部热点自动 Rust 化” 的流水线工具，它自己不做代码翻译，它做的是编排 ——profile、录制、生成脚手架、驱动编码 Agent 写 Rust、验证、切换、基准测试、出报告。

再看看它自己的 Cargo.toml，能看出作者对这个工具的定位：

这里有个值得注意的细节：主二进制只有四个直接依赖 ——anyhow、clap、libloading、serde。没有内嵌 LLM SDK，没有向量数据库，没有庞大的推理框架。这说明所有 AI 相关的能力都在外面，fast-anything 本体是一个纯粹的、不含模型的确定性工具。

这个设计决定非常重要，我后面会展开讲。

它自己带的 description 一句话：” 找出你应用里慢的那 5%，让你的编码 Agent 只把那个改写成 Rust，然后证明它行为依然一致。”

三、核心机制：为什么它敢让 Agent 写 Rust

整个项目最核心的技术难题，不是” 怎么调用 Agent”，而是怎么让 Agent 写的 Rust 是对的。

作者选择的答案是：录制 + 回放。

3.1 录制：把真实调用变成测试用例

fast-anything port 这一步会重新跑一遍你的应用，用探针捕获目标函数的每一次真实调用 —— 参数是什么、返回值是什么、调用了多少次 —— 最多记录 500 条。

这 500 条不是随便造的测试用例，是你的真实生产工作负载。这跟传统单元测试有本质区别：单元测试是开发者拍脑袋想出来的边界，而录制下来的是” 这个函数在真实数据上到底被怎么用的”。

作者在 README 里把这套东西叫做 “Proof, not vibes”（要证据，不要感觉）。这四个字基本是整个项目的设计哲学。

3.2 回放：Rust 版必须逐条对上

fast-anything verify 会用 release 模式编译 Rust 移植版，然后把录制的每一条调用逐条喂进去，逐字节比对输出。

不一致？直接拒绝启用。

这里有个细节我觉得很值得学。README 提到一个真实案例：

那个移植版看起来是对的，但它比较的是字节而不是字符。500 条真实调用里有 148 条抓到了它。

翻译一下：Rust 里 String 是 UTF-8 字节序列，chars() 才是 Unicode 码点。Python 的 str 是码点序列。如果 Agent 直接用 Rust 字节切片去模拟 Python 的字符串操作，遇到中文、emoji、组合字符就会出错。

而这条错误用普通单元测试很难发现，因为你得特意去构造非 ASCII 输入。录制回放天然就撞上了，因为你的真实数据里有中文。

3.3 派生用例：让原实现自己出题

光有录制还不够。录制只能覆盖” 过去发生过的事”，覆盖不了” 未来可能发生的事”。所以 fast-anything 会在录制的基础上自动派生额外的边界用例，并且 —— 这是最巧妙的地方 —— 让原实现来回答这些派生用例。

派生出来的边界包括：

  • NaN
  • 正负无穷（±infinity）
  • 负零（-0.0）
  • 零和一、负一
  • 非 ASCII 文本（带重音的字母、CJK 字符、emoji、组合标记）
  • 空输入
  • 最大到 16 倍大的输入

另外还有一类叫 shrunk inputs（收缩输入）：把原始输入切成更小的片段（极小的切片、随机的切片），然后仍然让原实现回答。

这个” 让原实现回答” 的思路是整个方案里我认为最漂亮的一处。派生用例是工具生成的，那么” 正确答案” 从哪来？答案是：从原实现那里拿。你不需要知道正确答案是什么，你只需要新实现和旧实现给出同一个答案。

这就把它从” 模糊测试 + 人工审查” 变成了” 差分测试（differential testing）”，而且是自动化的差分测试。

3.4 三重否决

综合起来，一个移植版要活下来得同时满足三件事：

  1. 值一致：浮点数允许 1e-9 的误差范围内
  2. 错误一致：原实现抛异常的地方，Rust 版也得抛同样的异常类型
  3. 不更慢：单次调用比原实现还慢的移植版，不允许启用

第三条特别务实。作者的解释很直白：跨语言调用本身有开销，如果调 Rust 的成本超过了省下的计算，那就白折腾了。

想强行启用可以，enable --force。

关于异常类型，CHANGELOG 里 0.6.2 有一条修正很能说明作者的态度：

Python verify only accepts the exception type the original raises; a Rust panic no longer counts.

Rust 里 panic 是一种语言级崩溃，不是 Python 的异常。移植版里 panic 崩掉了，被 catch 住假装抛了个异常 —— 这在 PyO3 场景下是能混过去的。作者专门修了这个洞，说明他真的在认真做验证这件事，而不是写个样子。

3.5 边界回退开关

FAST_ANYTHING_DISABLE=1 可以让任何一次运行都走原始实现。

这是个很关键的设计。你随时可以” 撤销”，代价是一次环境变量。这意味着这个工具不要求你相信它，它要求你先小范围试用。

四、它怎么知道该优化哪个函数

scan 这一步用各语言自己的 profiler 跑一次应用，然后把函数按一个综合指标排序 ——README 的原话是 “ranks functions by time × how portable they are”，也就是耗时 × 可移植性。

这个乘法很关键。一个占 40% 耗时但读了全局环境变量的函数，不可移植；一个占 3% 耗时但完全纯函数的函数，也不值得移植。真正该被挑出来的是那些既慢又干净的函数。

作者在给 Agent 的 SKILL.md 里写了一条明确的纪律：

Skip anything under 2% of the run: porting it can’t make a visible difference.

（运行耗时低于 2% 的直接跳过，移植它看不出区别。）

而且如果某个函数因为 I/O、随机性、全局状态、住在入口脚本里等原因没法移植，scan 会明确告诉你为什么现在还不能挪，而不是默默跳过。

各语言的 profiling 后端也是各用各的现成方案，从 CHANGELOG 能看到：

语言 Profiling 方式 源码解析 调用桥接
Python 探针 AST PyO3
JavaScript / TypeScript 探针 + worker_threads AST napi-rs
Ruby 探针 — C ABI + JSON（Fiddle）
Java Flight Recorder javac 自身解析器 FFM API
Kotlin 同 Java — Java 桥接
Go pprof — Windows loader / dlopen
PHP 每函数一行计时器 PHP tokenizer FFI 扩展
C / C++ 自己构建应用 — LoadLibrary / dlopen
C# / .NET 8+ EventPipe 采样器 Roslyn NativeLibrary

看到 C# 那一行了吗？”Profiled with the runtime’s own EventPipe sampler (nothing to install)”。作者没有为了支持 .NET 去引入一个第三方 profiler，而是用运行时自带的。这就是” 用现成的东西” 的思路。

Go 那行也有讲究：CHANGELOG 0.2.0 提到 “bench times a prebuilt binary so the compiler isn’t counted”。基准测试跑的是预编译的二进制，不然 Go 编译时间会被算进性能数据里 —— 这坑我踩过。

6.4 切换是怎么做到的

README 里说 enable / disable 的切换方式是 “one marked block, removed byte for byte”—— 一个带标记的代码块，禁用时逐字节原样移除。

这句话我反复看了两遍。它意味着：启用 Rust 移植版，你的原始函数体没有被改写，只是在文件末尾多了一个标记块，里面写着” 如果开了 Rust 路径，就走 Rust”。禁用的时候这个块被完整删掉，文件回到原样。

CHANGELOG 0.6.1 里有一条更能说明细节：

Node.js: … const functions port (declared with let while enabled, put back on disable)

JavaScript 里 const 声明的函数没法被重新赋值。所以启用的时候它临时改成 let，禁用的时候再改回 const。这种” 改回来” 的细节，作者是逐个语言处理的。

Node 那条还有个细节：0.6.1 说 “verify checks functions that aren’t exported”。也就是说，即使你的函数根本没被 export，verify 也会检查它 —— 因为移植版可能引用不到。

七、几个关键设计取舍

7.1 移植” 最外层循环”，而不是最内层函数

这是整个项目里我认为技术含量最高的一条决策。

README 举了个例子：fast-anything 移植的是它能拿到的最外层循环，连同它调用的辅助函数一起移植，这样应用只跨一次语言边界进入 Rust，而不是跨几百万次。

对比数据很直观：

Porting only the inner levenshtein gave 35× and 1.9×.

只移植最内层的 levenshtein，Python 侧得到 35 倍、PHP 侧只有 1.9 倍。而移植最外层循环，Python 是 116 倍，PHP 是 55 倍。

原因很直观：每次跨 FFI 边界都有固定成本（参数打包、类型转换、调用开销）。移植一百万次 vs 移植一次，差了六个数量级。

这个洞察对任何” 局部优化” 方案都成立，包括不用 Rust 的场景。跨语言边界是极其昂贵的东西，能不跨就不跨。

7.2 “移植版比原版慢就不启用”

前面提过，但值得单独强调，因为这体现了作者对” 性能优化” 这件事的理解。

很多人做优化会陷入” 只要更快就是好的” 的误区。但 fast-anything 明确把” 单次调用不比原实现快” 列为不启用条件。因为对于一个被调用一次的热函数，跨语言开销就是净亏损。

enable --force 可以绕过，但我猜作者自己也不建议用。

7.3 C ABI + JSON 作为通用桥接

看支持的语言列表，会发现一个规律：

  • Python 用 PyO3（专门的绑定，类型映射更精细）
  • JavaScript / TypeScript 用 napi-rs（Node 生态的标准做法）
  • 其余七种语言（Ruby、Java、Kotlin、Go、PHP、C、C++、C#）统一走同一条 C 桥接

README 说得很清楚：

Ruby, Java, Go, PHP, C, C++ and C# need no headers, bindings or extra tools: the port is a plain Rust
library with one C entry point taking and returning JSON, and fast-anything replays the recorded calls
against it directly. Any language that can call C can use that bridge.

（任何能调用 C 的语言都能用这条桥接。）

统一 C ABI + JSON 的代价是序列化开销，收益是零依赖 —— 不需要为每种语言写绑定、不需要用户装头文件、不需要额外工具链。这对” 支持十种语言” 这个目标来说是极其划算的取舍。

而且 0.2.0 有一条：

Ports for the C-bridge languages are now verified by fast-anything itself, in a child process, so a
crashing port can’t take it down.

C 桥接的移植版在子进程里验证，崩了也带不垮主进程。考虑到移植版是 Agent 自动生成的 Rust 代码，崩溃概率并不低，这个隔离是必要的。

7.4 缓存：所有移植版共享一个 .fast/target

README 提了一句：

Cache: every port shares one .fast/target. Delete it whenever you like.

每个移植版是一个独立的单函数 crate，但共享一个 target 目录，所以增量编译很快。

CHANGELOG 0.6.0 还有一条优化：

Ports rebuild about 4× faster after each edit (no LTO, parallel codegen; no measurable runtime cost).

改完之后重建快 4 倍 —— 做法是关掉 LTO、开启并行 codegen，运行时性能没有可测量的损失。

不过这里有个值得留意的矛盾：Cargo.toml 里主二进制的 [profile.release] 明确写着 lto = "fat"、codegen-units = 1。也就是说主工具本身用满 LTO，而生成的移植版 crate 不用。两者的性能诉求完全不同，这个区分是对的。

7.5 Agent 在环外，工具在环内

前面提到过，这是最关键的架构取舍。

fast-anything 的二进制依赖里没有任何 LLM SDK。这意味着：

  • 它不绑定任何模型供应商
  • 它不需要 API key
  • 它不会把你的代码发给任何第三方（除非你主动用 --agent claude）
  • Agent 只负责写 src/lib.rs 里的那段 Rust，所有判定逻辑都在确定性代码里

这个分工的价值在于：验证是可靠的。如果” 这个移植版对不对” 是由 LLM 判断的，那整个信任链就塌了。现在是：Agent 提方案，工具做裁判。

而且用 MCP 或 Skill 的话，你可以让模型完全在本地跑 ——--agent 接受” 任何从 stdin 读 prompt 的命令”，你完全可以指向本地的 ollama 或者别的本地 CLI。

八、实测数据

README 给了实测结果，环境是 i5-10500 / Windows 11（C 和 C++ 是 4 核 GitHub Actions Linux runner），可以从仓库的 examples/ 复现。

应用 优化前 优化后 加速
Python 模糊去重（700 个名字） 4.91s 42ms 116×
TypeScript 模糊去重（2,000 个名字） 3.11s 155ms 20×
PHP 模糊去重（600 个名字） 2.94s 53ms 55×
Go 模糊去重（3,000 个名字） 3.02s 144ms 21×
Ruby 模糊去重（400 个名字） 3.13s 228ms 14×
C# 模糊去重（4,000 个名字） 4.03s 312ms 13×
Java 模糊去重（4,000 个名字） 3.50s 1.18s 3×
C mandelbrot（8 个缩放级别） 431ms 127ms 3.4×
C++ 模糊去重（6,000 个名字） 3.02s 1.09s 2.7×

Java 那一行作者特别标注了：函数本身快了 11 倍，但整个进程只快 3 倍，剩下的都是 JVM 启动时间。

这个诚实我得夸。绝大多数性能工具会只报” 函数加速比”，fast-anything 报的是端到端，还额外把” 函数 11 倍但端到端 3 倍” 这种反直觉的情况标出来。因为对用户有意义的是端到端。

同样值得看的是 C 和 C++ 只有 2.7-3.4 倍。对比 Python 的 116 倍，差距在哪？

  • Python 本来就慢，FFI 边界开销占比小，Rust 的收益被放大
  • C / C++ 本来就快，同样的绝对节省量除以更小的分母，加速比自然低
  • 换句话说，这个工具在” 本来就慢的语言” 上收益最大，这符合直觉，也符合实际

另外注意所有数据都来自 examples/ 里的模糊去重这一个场景。这是一类典型的纯函数、CPU 密集、易移植的负载。所以这些数字应该理解为” 最好情况”，而不是” 平均值”。

九、和同类项目对比

这个赛道现在挺热闹的，我把几个有代表性的放一起说说。

9.1 vs. 整应用重写工具

最直接的对照组是 erkamyaman/rust-anything—— 那个项目也是帮 Agent 把代码改写成 Rust，1869 star 这个项目多少沾点它的影子（同一批爆火的”AI + Rust” 项目）。

区别在哲学：

维度 fast-anything 整应用重写类工具
目标 局部热点（慢的 5%） 整个模块或整个应用
验证方式 录制真实调用 + 差分回放 用例集比对、测试通过
用例来源 真实生产工作负载 生成的或手工写的
边界策略 移植最外层循环，最小化 FFI 次数 逐函数迁移
可逆性 标记块，byte-for-byte 移除 通常需要手工回滚
编译成本 单函数 crate，秒级 模块级 crate，分钟级

fast-anything 的核心优势是用例来源。差分测试的关键在于” 正确答案” 必须可信 —— 原实现就是标准答案。用例来自真实工作负载，比人工造的用例可信得多。

9.2 vs. 传统 profiler

py-spy、cProfile、pprof、perf、Java Flight Recorder 都是成熟工具，fast-anything 用的正是它们（或等价物）。

区别在于：profiler 只告诉你哪里慢，fast-anything 告诉你接下来该做什么。

传统 profiler 的工作流是：跑 profile → 看火焰图 → 手动改 → 再跑 profile → 对比。中间的” 改” 这一步是最耗时的，尤其当你要写 Rust 时。

fast-anything 把” 改” 这一步交给 Agent，并且提供” 证明它对了” 的机制。所以它不是替代 profiler，是接在 profiler 后面。

9.3 vs. Cython / Nuitka / PyO3 手写

这是 Python 生态里最成熟的方案。做同样的事，你会：

  1. 手写 Cython 装饰器或 PyO3 绑定
  2. 自己写对照测试
  3. 自己保证边界一致

fast-anything 的差异是验证是自动的、且基于真实数据。手写方案里，” 写对照测试” 这一步占了大部分工作量，而且最容易偷懒少写。

反过来，fast-anything 的产物不如手写方案干净 —— 它是在原文件末尾追加标记块，生成的 crate 是机器拼装的，不会符合你的代码风格。

9.4 vs. 通用 FFI 库（PyO3 /napi-rs/ JNI 等）

这些是底层零件，fast-anything 是用零件组装的产品。

它自己就用了 PyO3 和 napi-rs。所以严格说，fast-anything 是这些库之上的一层编排。

9.5 vs. Rust 生态的性能工具（Miri、cargo-flamegraph 等）

方向相反。Rust 生态的工具是优化 Rust 代码本身，fast-anything 是把别的语言变成 Rust。

十、真实局限

这部分我不想写得太客气，因为不写清楚就是害人。

10.1 只能移植” 纯函数”

这是最硬的限制。fast-anything 只移植顶层、确定性、接受普通数据类型的函数：

  • 数字、字符串、列表、字典、类型化数组
  • dataclass、NamedTuple、数值 NumPy 数组也算” 普通数据”
  • Python 里是模块级函数和 @staticmethod
  • Java / C# / PHP 是静态方法，Go 是普通函数，C/C++ 是自由函数和静态方法

不能移植的：读写 I/O、依赖随机数、依赖全局状态、依赖环境变量、依赖数据库连接、跨函数有副作用的逻辑。

如果你的热点函数读了一个全局配置，这个函数就动不了。

不过作者给了一条出路 —— 在 SKILL.md 里：

Suggest moving pure logic into its own module when that’s the blocker.

先重构出纯函数，再移植。人工做这步有点烦，但这确实是唯一正确的路径。

10.2 性能收益高度依赖场景

前面已经说了：README 的数据全部来自” 模糊去重” 这一类 CPU 密集的纯函数负载。

如果你的应用是 I/O 密集（大量数据库查询、HTTP 请求），那” 慢的 5%” 很可能根本不是 CPU 部分，Rust 帮不上什么忙。反过来说，工具会自动告诉你热点在哪 —— 但它不会说” 你的问题不该用 Rust 解决”。

10.3 移植版代码需要人看一眼

这是最容易被忽略的一点：Agent 写的 Rust 会留在你的仓库里。

fast-anything 验证了行为一致，但没有验证：

  • 代码风格是否合规
  • 有没有引入 panic 路径
  • unsafe 块用得对不对
  • 是否有隐蔽的资源泄漏
  • 是否符合你的 lint 规则

一个只有 anyhow、clap、libloading、serde 四个依赖的工具生成出来的 Rust，大概率是” 能跑但不好看” 的代码。你多半还是要手工整理一遍。

说白了：它证明了” 对”，但没有保证” 好”。

10.4 需要 Rust 工具链

虽然是” 局部重写”，你还是得装 rustup、装 Rust 工具链。对纯 Python 团队来说这是个不小的门槛 ——CI 镜像也得跟着改。

10.5 项目太新

创建于 2026 年 11 月 21 日，到我写这篇的时候只有两天。

  • 版本号才 0.7.0，还没到 1.0
  • 56 个提交
  • CHANGELOG 显示迭代非常快（0.1.0 到 0.7.0），0.6.2 里还有个修 npm 启动器执行位的 bug
  • 大量功能是最近才加的

作者迭代速度是优点，但也意味着很多东西还在动。0.7.0 才刚加的 JavaScript Bun/Deno 支持、Node worker_threads 支持，多半还没被多少人踩过。

我个人建议：先用它跑一遍你的项目看效果，别急着在生产主链路上依赖它。

10.6 需要 Agent，有 Token 成本

go --agent claude 意味着每次移植都要调一次大模型。这个成本在高频迭代的场景下会累积。

十一、适合谁，不适合谁

适合

1. 有明确的 CPU 热点，但不想整体重写的团队

这是我最推荐的场景。你已经知道某个函数慢，或者至少能接受跑一次 scan 看看。改写范围可控，出问题能一键回退。

2. 正在用 AI 编码 Agent，但被”Agent 写的代码不知道对不对” 折磨的人

这是 fast-anything 最核心的用户画像。Agent 写 Rust 很快，但验证是人的活。这个工具把验证自动化了。

3. Python / Ruby / PHP 这类” 动态语言但有性能需求” 的后端

116 倍、55 倍、14 倍 —— 这些数字不是噱头，是真实场景下能拿到的收益。

4. 想做 A/B 对比” 到底值不值得重写” 的人

bench 会给你一个真实答案，而且 disable 随时能回退。这比开三天会做技术选型靠谱。

不适合

1. 性能问题的根因是 I/O 而不是 CPU

先别折腾 Rust。先看看你的数据库索引、缓存策略、连接池。99% 的” 慢” 是 I/O 问题。

2. 团队没有 Rust 能力，也不打算有

你需要有人能看懂 Agent 生成的 Rust，能在 verify 失败时去修。哪怕只是一个会读 Rust 的同事。

3. 需要维护长期稳定性的核心链路

这个工具两天大、0.7.0 版。它目前更适合当” 探索工具” 和” 优化工具”，而不是” 运行时依赖”。

4. 依赖复杂对象或副作用的业务逻辑

热点函数如果牵扯 ORM session、请求上下文、事务，这些都过不了” 纯函数” 这一关。

5. 已经在用 Cython / Nuitka 并且维护得不错的老项目

没必要为了换工具而换工具。

十二、我的实际建议

如果你想试，我建议这么开始：

第一步，先只做 scan，别急着 port。

看看你的热点分布。如果发现” 慢的 5%” 里没有明显的纯函数热点，那这个工具对你没用，直接放弃，成本也就几分钟。

第二步，挑一个孤立的、调用量大的小函数试。

别一上来就动核心逻辑。找个边缘功能试水，跑通完整流程。

第三步，看 verify 的输出，重点看派生用例。

如果录制用例全过但派生用例挂了，说明这个函数有边界行为你没考虑到 —— 这正是这个工具最有价值的时刻。哪怕你最后决定不用它，这个发现也有价值。

第四步，bench 看端到端，别只看函数加速比。

Java 那个” 函数 11 倍、端到端 3 倍” 的例子就在眼前。

第五步，生成 PR 报告再合并。

report 会出 markdown + SVG 卡片。这东西贴到 PR 里，评审的人一眼就知道哪些调用被验证过、覆盖了多少条用例。这在 code review 里太有用了。

十三、这个项目折射出的更大趋势

抛开工具本身，fast-anything 让我注意到一个正在发生的变化。

过去我们说”AI 写代码”，瓶颈从来不是写，是验证。你让模型写一个函数只要 10 秒，但证明这个函数跟原来那个 300 行的函数在所有输入下行为一致，可能要花一天。

所以真正有价值的 AI 编程工具，不是让模型写得更快，而是让验证变得便宜。

fast-anything 的整个设计 —— 录制、差分回放、派生边界用例、让原实现当标准答案 —— 本质上是在做一件事：把” 相信我” 变成” 这里有 500 条证据”。

这个思路可以套用到任何领域：

  • 数据库迁移工具：新旧 schema 跑同一批查询，比对结果
  • API 重构：录制真实 HTTP 请求，新旧实现回放比对响应
  • 编译器优化：同一份输入，编译前后输出必须逐字节一致
  • 性能优化框架：录制真实负载，替代拍脑袋造的 benchmark

事实上我怀疑 rust-anything 和 fast-anything 这两个项目本质上是同一类工具的不同实现，都是在解决”AI 写的东西怎么证明对”。这两个项目在 11 月中下旬前后同时爆火，1869 和 3321 star，说明这个需求是真的存在，不是一时的风口。

从这个角度看，fast-anything 最值得学的地方可能不是它的 Rust 流水线，而是那个差分测试的思路：把原实现当作唯一可信的标准答案，用真实工作负载当测试用例，让工具去做机械的、容易出错的验证工作。

这套东西在别的地方也用得上。

十四、结语

回到开头那个需求 ——“用 Rust 重写一下那个 Python 服务”。

如果今天有人这么问我，我会反问三个问题。但现在我至少能给出一个可执行的路径了：

先看热点，再决定。数据说话，不拍脑袋。

这可能才是 2026 年” 让 AI 重写你的代码” 这件事的正确打开方式 —— 不是全量重写，是增量替换，是每一步都带着证据。

至于要不要真的用起来，我得说：先在边缘功能上试，别在核心链路上梭哈。项目两天大，还在快速迭代。

但这个方向，我看好。
